## See which project an item belongs to

**Who:** Operator

**What:** Every row in the priority list shows its owning project, the same way the Backlog already does.

**Why:** So when I'm working across multiple projects at once, I can tell at a glance which one each piece of work belongs to, without opening it.

**Activity:** Get oriented on the pipeline - See the whole pipeline at a glance - what's active, blocked, waiting on me, and queued - the moment it changes, as long as the dashboard is running.

**Step:** Review current work status

**Status:** ready

### Acceptance Criteria

- Given an item appears in the priority list - needs-attention, active, or queued, when it renders, then its owning project is shown alongside it, so it's attributable at a glance without opening it.
- Given an item has no registered project, when it renders, then the project field is blank, same convention as the Backlog.

### Context

The project shown here isn't a field already sitting on the node ready to read. In the engine, `Node` does carry its own `project` column, but the Backlog use case this story explicitly matches doesn't read it - it derives project through `project_of()`, which looks up the item's "repo" artifact via a separate store call, not the node's own `project` field. Reproducing "the same way the Backlog already does," including the blank-when-unregistered behaviour in AC-2, means reusing that same artifact-based derivation rather than the node's `project` column, since the two are populated independently and can disagree.
