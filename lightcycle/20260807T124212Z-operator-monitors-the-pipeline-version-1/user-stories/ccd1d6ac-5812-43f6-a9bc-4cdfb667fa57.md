## Open a node from the hierarchy

**Who:** Operator

**What:** Selecting any node - theme, item, or step - opens it into its own tabbed hub, the same kind of view regardless of node type.

**Why:** So navigating the hierarchy doesn't behave differently depending on what kind of node you land on.

**Activity:** Inspect one item's journey - Understand a specific item end-to-end - its artifacts, child steps, and logs - to see what happened or why it's stuck.

**Step:** Explore the hierarchy

**Status:** ready

### Acceptance Criteria

- Given any node (theme, item, or step) is selected in the hierarchy, when I confirm the selection with Enter or →, then it opens into its own tabbed hub, landing on the tab that matches its state.
- Given the selected node is a step rather than a theme or item, when its hub opens, then the header shows its role and state in place of the theme/workflow/description fields, which only apply to themes and items.

### References

- [wireframe-hub.html#hierarchy](../wireframes/wireframe-hub.md)

### Context

AC-2's step header needs role, but the trace data the Hierarchy tab reads a step's fields from doesn't carry it today - `TraceUseCase`'s `TraceNode` (id, step, state, log) omits role, even though the `Node` it's built from has it. Delivering this story means closing that gap - extending `TraceNode`, switching the step read to return `Node` objects, or another shape - which the API Contracts artifact already flags as a genuine build-time choice, not a design decision already settled.
