## View a text artifact full-screen

**Who:** Operator

**What:** A text artifact (e.g. a spec) opens full-screen within the dashboard.

**Why:** So I can read it without leaving the terminal.

**Activity:** Inspect one item's journey - Understand a specific item end-to-end - its artifacts, child steps, and logs - to see what happened or why it's stuck.

**Step:** View an artifact

**Status:** ready

### Acceptance Criteria

- Given an artifact declares kind `text`, when I select it with Enter or →, then it opens full-screen, scrollable if longer than one page.
- Given the text artifact is open, when I scroll, then I can read the whole thing without truncation.
- Given an artifact declares a kind the TUI does not recognise, when I select it, then it opens in the text viewer rather than failing, so no artifact is ever unopenable.

### Context

Text is the fallback renderer for the whole artifact viewer. Every artifact value is a string at rest, so text is always a valid last resort - which makes rendering a total function and means an artifact attached by a future workflow, declaring a kind this TUI has never heard of, is never invisible. It is plainly rendered instead. This is what lets the engine avoid gatekeeping which kinds a workflow may express.

The `kind` field these acceptance criteria dispatch on doesn't exist in the engine yet: `Artifact` today is only `type`, `value`, `label` (`lightcycle/domain/work/artifact.py`), and `link_artifact.py`'s `LinkArtifactInput` still takes `item`/`atype`/`value`/`label`/`replace` - no `kind`, no attach-time resolution order. Opening a text artifact by its declared kind, or falling back to text for one the TUI doesn't recognise, isn't buildable until Change 1 in tui-architecture.md lands - and that document is explicit that its engine changes are this design's own delivery, not a prerequisite filed elsewhere, so this story can't disclaim the gap as out of scope.
