## See each node's id, status, and role in the hierarchy

**Who:** Operator

**What:** Every node (theme, item, or step) shows its current state (todo, active, blocked, done, queued); step nodes also show which role performed or is performing them; a node blocked on another item's completion shows a dependency indicator.

**Why:** So I can tell what's worth investigating, and who did it, without opening each one.

**Activity:** Inspect one item's journey - Understand a specific item end-to-end - its artifacts, child steps, and logs - to see what happened or why it's stuck.

**Step:** Explore the hierarchy

**Status:** ready

### Acceptance Criteria

- Given a node in the hierarchy, when it renders, then its own real id (e.g. LC-143.3.4) is shown alongside its title, and its current state is shown using the same labels/icons/colours as the priority list.
- Given a node's state changes while the hierarchy is open, when that happens, then it updates without a manual refresh.
- Given a step node has been performed, or is being performed, by a worker, when it renders in the hierarchy, then its role (e.g. write-code, review-code) is shown alongside its state.
- Given a step node is a human step, when it renders, then no role is shown for a worker that doesn't exist.
- Given a node is blocked on another item's completion, when it renders in the hierarchy, then a dependency indicator is shown alongside its state, distinct from other blocked reasons.

### Context

AC-4's "no role is shown" doesn't mean the role slot goes empty for human steps - the cited wireframe renders the literal text "human" there (LC-143.3.3 spec-await-merge, LC-143.3.8 code-await-merge), and the live engine treats role == "human" as a real, first-class value rather than an absent one (state.py's lane_for, node_queue.py's queue filter both branch on it explicitly). The distinction this AC is actually drawing is worker-role name (write-code, review-code, open-pr, watch-ci) versus the human role, not role versus no role at all.
