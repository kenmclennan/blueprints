## Filter the backlog by project

**Who:** Operator

**What:** Pressing f opens a picker - a navigable list of registered projects, plus 'All' - rather than cycling through them one keypress at a time.

**Why:** Cycling doesn't scale once there are more than a handful of projects; a picker stays a constant-time interaction regardless of how many exist.

**Activity:** See what's coming next - Know what's waiting in the backlog so nothing surprises me.

**Step:** See the todo backlog

**Status:** ready

### Acceptance Criteria

- Given I press f, when the picker opens, then it shows 'All' plus every registered project, each with its own item count, navigable with up/down.
- Given the picker is open, when I select a project and press Enter, then the backlog filters to only that project's items and the picker closes.
- Given the picker is open, when I press Esc, then it closes without changing the current filter.
- Given a filter is active (or 'All' is selected), when I look at the filter bar, then it shows only the current filter's own item count, not a breakdown of every project.

### Context

Per-project item counts aren't available from the current read surface: `BacklogUseCase.execute` (`lightcycle/application/work/backlog.py`) returns rows for whichever single `project` filter it's given, plus an optional `groups` breakdown - but nothing that returns every registered project's own count at once, independent of which filter is active. AC-1's picker needs exactly that (every registered project, each with its own count, before any filter is chosen) - a genuine read-surface gap (see api-contracts.md), not something the TUI can derive by calling the existing use case once per project. Sibling story addfdbfd hits the adjacent problem (empty-overall vs. empty-under-filter) for the same underlying reason: today's read surface only ever answers for one filter value at a time.
