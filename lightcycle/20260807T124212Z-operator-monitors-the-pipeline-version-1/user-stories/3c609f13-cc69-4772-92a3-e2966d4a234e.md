## See a done step's historical log

**Who:** Operator

**What:** Opening the Log tab for a step that's already finished shows its full accumulated output as a static, scrollable read - not a live tail.

**Why:** So I can review what happened after the fact, the same way I'd check a live step, without waiting on something that's already over.

**Activity:** Inspect one item's journey - Understand a specific item end-to-end - its artifacts, child steps, and logs - to see what happened or why it's stuck.

**Step:** Stream the current step's live log

**Status:** ready

### Acceptance Criteria

- Given the current step is done, when I open its Log tab, then it shows the complete log output captured from that step's run.
- Given a done step's log is open, when I view it, then no live-tail behaviour is shown - no 'live' indicator, no auto-scroll - since nothing new will arrive.
- Given the done step's log is longer than one screen, when I press Ctrl+U or Ctrl+D, then I move through it a full screen at a time, same as the live log.

### Context

The engine has no durable step-to-log-path record today: both `TraceUseCase._log_for_step` and `ResolveLogUseCase` resolve a step's log purely by scanning the live workers registry (`workers.json`) for an entry whose `step` field matches, and that registry is trimmed to a bounded `worker-history` depth by the pool's sweep (`prune_workers`, called from `application/pool/sweep.py`). A done step's worker entry surviving long enough to still be found there isn't guaranteed - once pruned, the current lookup returns nothing for that step, even though the underlying log file itself is never deleted from `logs/`. Resolving a done step reliably to its historical log is therefore one of the read-model gaps the architecture's Change 4 leaves for the build to close, not something the engine's existing read-only use cases already give the TUI for free.
