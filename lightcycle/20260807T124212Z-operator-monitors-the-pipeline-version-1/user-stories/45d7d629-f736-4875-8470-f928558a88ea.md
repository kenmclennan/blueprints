## See the item's current step, role, and elapsed time

**Who:** Operator

**What:** The detail view names which step is current, which role is performing it if a worker is, and - for an active item - approximately how long it's been running.

**Why:** So I know exactly what kind of work is happening or waiting to happen, without a separate trip back to the list to check timing.

**Activity:** Inspect one item's journey - Understand a specific item end-to-end - its artifacts, child steps, and logs - to see what happened or why it's stuck.

**Step:** Find the item

**Status:** ready

### Acceptance Criteria

- Given an item's detail view is open, when I look at it, then it names the current step.
- Given the current step is performed by a worker, when I look at the detail view, then it names the role (e.g. write-code, review-code).
- Given the item is active, when I look at the detail view, then it shows an approximate elapsed time, matching the list's format (e.g. '14m', '1h 7m').
- Given the current step is a human step with no worker, when I look at the detail view, then no role or elapsed time is shown for a worker that doesn't exist.

### Context

STEP and ROLE are two independent fields on the node (`role`, `step` in `lightcycle/domain/work/node.py`), not one derived from the other. The wireframe's Hierarchy tab shows this directly: sibling steps like `spec-open-pr` and `code-open-pr` both carry role "open-pr", distinct from their own step id, so the value shown for ROLE cannot be assumed to equal the step's name - it has to be read from the node's own role field. The AC-4 case (human step, no role/elapsed shown) corresponds to role literally holding the string "human" - the same sentinel `node_queue.py` and `state.py` use to route human work to its own lane (`role == "human"`) - not to role being null or absent, so detecting it is a value comparison against that string, not a presence check.
