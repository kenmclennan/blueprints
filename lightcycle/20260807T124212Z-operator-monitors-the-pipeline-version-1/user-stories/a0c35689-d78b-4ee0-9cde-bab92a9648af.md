## See todo items not yet activated

**Who:** Operator

**What:** Lists items still in todo state, not yet planned/active.

**Why:** To know what's waiting to be picked up later.

**Activity:** See what's coming next - Know what's waiting in the backlog so nothing surprises me.

**Step:** See the todo backlog

**Status:** ready

### Acceptance Criteria

- Given items exist in todo state, when I switch to the backlog, then they're listed.
- Given a todo item is later activated, when that happens, then it no longer appears in the backlog.
- Given the backlog is longer than one screen, when I press Ctrl+U or Ctrl+D, then the view jumps by roughly a full screen at a time.
- Given an item appears in the backlog, when it renders, then its owning project is shown alongside it, so it's attributable at a glance without opening it.

### References

- [wireframe-backlog.html#normal](../wireframes/wireframe-backlog.md)

### Context

The query side of this already exists: `BacklogUseCase` (lightcycle/application/work/backlog.py) already selects items in `State.BACKLOGGED`, already supports a project filter, and already returns each row's owning project via `HumanNodeRow.project` - nullable for unscoped items, which is why the wireframe's project column is blank for most rows and populated only for the one tagged item. `lc backlog` already renders this data today, but only as a static one-shot print (`render_backlog` in lightcycle/render.py returns a flat list of pre-formatted lines with no interactive state), with no cursor, selection, or paging. This story's real work is building the interactive TUI screen - cursor movement, Ctrl-U/Ctrl-D paging - over that existing, already-correct data path, not the backlog query or project-attribution logic itself.
