## Land on the tab that matches the item's status

**Who:** Operator

**What:** Opening a node lands on whichever of Hierarchy, Log, or Artifacts is most useful for its current state: Log for an active item, Artifacts for a needs-attention item on a human step or for a done item, Hierarchy for one blocked on a dependency, still queued, or a theme.

**Why:** So the first thing I see is the most relevant thing, not a menu I have to choose from every time.

**Activity:** Inspect one item's journey - Understand a specific item end-to-end - its artifacts, child steps, and logs - to see what happened or why it's stuck.

**Step:** Find the item

**Status:** ready

### Acceptance Criteria

- Given the node is active (a worker is performing its current step), when I open it, then it lands on the Log tab.
- Given the node is a needs-attention item on a human step (e.g. await-merge, or rejected/needs rework), when I open it, then it lands on the Artifacts tab.
- Given the node is blocked on another item's completion, or is still queued/not yet run, when I open it, then it lands on the Hierarchy tab.
- Given the node is done, when I open it, then it lands on the Artifacts tab, same as a needs-attention item on a human step.
- Given the node is a theme, when I open it, then it lands on the Hierarchy tab, since a theme has no single item-level state of its own to key a different default off.

### Context

The "needs-attention" classification this story keys off (AC-2) isn't this story's to invent - the sibling activity "Get oriented on the pipeline" already establishes it as one of the three priority-sort buckets on the main dashboard (needs-attention, active, queued), so this story's tab-routing has to land on whatever that bucketing settles a node into, not derive a parallel definition of its own. In the real engine that bucketing isn't a single field: Node.attention (lightcycle/domain/work/node.py) is a manual/escalation flag - set via `lc add --inbox` or by specific outcomes like the pending-feedback path in complete_step.py - separate from the step-ownership check (`role`/`owner_of` in lightcycle/domain/flow/flow.py) that lane_for() in lightcycle/domain/work/state.py uses to route a human-owned step to Lane.INBOX. A plain await-merge step carries no attention flag of its own, so the two signals need to be reconciled by whichever story owns the bucket definition, not treated as interchangeable.
