## See when a newer version is available

**Who:** Operator

**What:** The footer status bar indicates when a newer lightcycle release exists.

**Why:** So I know to upgrade without checking manually, and without it competing for space with whatever I'm actually working on.

**Activity:** Get oriented on the pipeline - See the whole pipeline at a glance - what's active, blocked, waiting on me, and queued - the moment it changes, as long as the dashboard is running.

**Step:** Launch the dashboard

**Status:** ready

### Acceptance Criteria

- Given a newer version exists upstream, when the dashboard checks, then the footer shows an 'upgrade available' indicator with the newer version number.
- Given the installed version is current, when the dashboard checks, then no upgrade indicator is shown.
- Given the upgrade check can't complete (e.g. no network), when that happens, then the footer just omits the indicator rather than erroring or blocking anything else.

### Context

The engine already has an upgrade-check mechanism behind `lc upgrade` (`lightcycle/application/setup/upgrade.py`): `fetch_remote_version()` fetches `__version__` from `__init__.py` on the repo's GitHub `main` branch (a 10s-timeout HTTP fetch, not PyPI - lightcycle installs via `pipx install git+...`) and compares it to the running version via a semver tuple compare, and `upgrade()` already exposes a `check_only=True` mode that runs exactly this check without touching the venv-busy guard or installing anything - the read path this story needs, not a new mechanism to build. That module sits outside the `application/work/` read-only use-case layer `tui-architecture.md` scopes the TUI's engine interaction to, and the rest of `upgrade()` can install and can raise `VenvBusyError` on a busy venv - the TUI must call it strictly in `check_only` mode and never exercise the install branch.
