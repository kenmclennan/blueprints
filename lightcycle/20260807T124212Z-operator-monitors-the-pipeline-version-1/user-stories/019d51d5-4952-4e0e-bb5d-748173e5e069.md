## See queued items at the bottom

**Who:** Operator

**What:** Ready-but-unclaimed steps appear last, below active work.

**Why:** So what's coming doesn't compete for attention with what needs me now.

**Activity:** Get oriented on the pipeline - See the whole pipeline at a glance - what's active, blocked, waiting on me, and queued - the moment it changes, as long as the dashboard is running.

**Step:** Review current work status

**Status:** ready

### Acceptance Criteria

- Given queued items exist, when I view the list, then they appear below active items, differentiated by their own label/icon/colour.
- Given a queued item is claimed and becomes active, when that happens, then it moves from the queued group into the active group.
- Given a row's title is longer than one line, when it doesn't fit, then it wraps to a second line rather than being truncated with an ellipsis.
- Given a queued item, when it appears in the list, then its next step name is shown.

### Context

"Queued" is an existing engine concept, not a grouping this TUI invents: `lane_for(state, role)` in `lightcycle/domain/work/state.py` puts a step in the `queue` lane only when it's `ready` and its role isn't `human` - a ready step already escalated to the operator lands in `inbox` instead, never `queue`, so it belongs with the attention group above, not this one. Two use cases already compute lanes differently - `StatusUseCase` (`lightcycle/application/work/status.py`) returns a `lanes` dict keyed by lane name, with `queue` and `blocked` as separate keys, while `QueueUseCase` (`lightcycle/application/work/queue.py`, behind `lc queue`) merges the two into one - and only the separated form matches this wireframe, where blocked/dependency items (the ⛓ rows) sit in the top attention group rather than the bottom queued one.
