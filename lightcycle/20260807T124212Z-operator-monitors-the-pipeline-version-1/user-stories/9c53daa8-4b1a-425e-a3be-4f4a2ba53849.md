## See which nodes have content

**Who:** Operator

**What:** Each node in the tree shows a small indicator when it has at least one non-internal artifact attached.

**Why:** So I can spot which nodes are worth opening without checking each one individually.

**Activity:** Inspect one item's journey - Understand a specific item end-to-end - its artifacts, child steps, and logs - to see what happened or why it's stuck.

**Step:** Explore the hierarchy

**Status:** ready

### Acceptance Criteria

- Given a node has at least one artifact whose internal flag is false, when it appears in the hierarchy, then it shows a content indicator.
- Given a node has only internal-flagged artifacts, or none at all, when it appears in the hierarchy, then no content indicator is shown.
- Given the content indicator is shown, when I open that node, then at least one artifact I can actually view is there.

### Context

Live-store analysis (2026-07-23) found artifact-presence alone isn't discriminating - 73% of items and 66% of steps have at least one. But most of that on steps is internal bookkeeping, not content: `reflection` (retro/audit), `resolved-by`/`resolves` (backlog cross-linking), `watched-step`/`feedback-watermark`/`feedback-spawned-through` (PR-watch dedup) are written by three specific engine modules purely for the engine's own algorithms, never meant for a human to open. `repo`/`branch` are also engine-written but ARE genuine content, so "engine-written" isn't the right test either - it's specifically those three modules' bookkeeping types.

The wireframe's hierarchy state (wireframe-hub.html#hierarchy) doesn't actually render a content indicator - every row's icon column is identical regardless of content (○ for a normal row, ▸ for the current one) - so the indicator's glyph and where it sits in the row aren't specified by anything this story cites and are left to the build. The underlying data is already there to filter, though: `children()` in `sqlite_store.py` hydrates each returned `Node` with its own `artifacts` list the same way `item_artifacts()` does for the Artifacts tab, so once change 1 (the `internal`/`kind` fields) lands, the indicator is a filter over a field the hierarchy's read model already carries per node, not a new query.
