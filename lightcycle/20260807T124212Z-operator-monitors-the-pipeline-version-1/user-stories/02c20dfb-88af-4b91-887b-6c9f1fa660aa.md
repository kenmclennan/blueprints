## See whether Claude is available to process work

**Who:** Operator

**What:** A footer status segment, next to pool status, shows whether Claude is currently available to process work - and when it isn't, when it will next be probed for recovery.

**Why:** So I immediately understand the pipeline has stalled because Claude rejected a worker (usage limits or similar), not because the pool itself is down or something else is stuck - without digging through logs to tell the difference.

**Activity:** Get oriented on the pipeline - See the whole pipeline at a glance - what's active, blocked, waiting on me, and queued - the moment it changes, as long as the dashboard is running.

**Step:** Launch the dashboard

**Status:** awaiting-review

### Acceptance Criteria

- Given the circuit breaker is closed, when I view any screen, then the footer's status line shows "claude available" in its default styling, next to the pool status.
- Given the circuit breaker is open, when I view any screen, then the footer's status line shows "claude unavailable" plus the time it will next probe for recovery (e.g. "resumes 14:32:00"), styled as an alert.
- Given the breaker opened while a step's worker was running and that worker was killed and reclaimed back to ready, when I open that node, then the hub shows its real current state (queued, not active) - the same reclaim behavior the engine already applies to any lost worker, not new behavior this indicator introduces.
- Given the breaker closes again, when the next poll runs, then the footer returns to "claude available" without requiring a restart.

### Context

This indicator is drawn on three of the four wireframes (Priority List, Backlog, Node Hub) but had no story until this one - added after an adversarial buildability review of the exported design found it fully wireframed with no acceptance criteria to build against, and the screen-flow diagram's own "what's deliberately left off" footnote was stale relative to it (design-packet review, 2026-08-07).

The read path it needs doesn't exist yet: api-contracts.md's "Breaker state has no read-only use case at all" finding is the concrete engine gap this story depends on - `is_open`/`reset_at` are real and persisted but only readable today via transient `lc start` log lines, not on demand.

AC-3 doesn't require new reclaim behavior: state-lifecycle.md's own state machine already documents `in_progress --> ready: worker lost, reclaimed` as standing engine behavior - a worker killed by any cause, breaker trip included, already returns to ready and re-enters the queue lane. The TUI just has to display that real state accurately; it isn't implementing a special case for the breaker.
