## See active items with elapsed time

**Who:** Operator

**What:** Active rows show an approximate running time (14m, 45s, 1h 7m).

**Why:** To judge whether something's taking longer than expected, at a glance.

**Activity:** Get oriented on the pipeline - See the whole pipeline at a glance - what's active, blocked, waiting on me, and queued - the moment it changes, as long as the dashboard is running.

**Step:** Review current work status

**Status:** ready

### Acceptance Criteria

- Given an item is active, when it appears in the list, then its row shows an approximate elapsed time (e.g. '14m', '45s', '1h 7m'), not exact seconds.
- Given an item's elapsed time is displayed, when time passes, then the value updates periodically without a full list refresh.
- Given active items exist, when I view the list, then they're grouped below needs-attention and above queued, differentiated by their own label/icon/colour.
- Given a row's title is longer than one line, when it doesn't fit, then it wraps to a second line rather than being truncated with an ellipsis.
- Given an active item, when it appears in the list, then its current step name is shown alongside its elapsed time.

### Context

Approximate, not exact seconds, because the poll interval is 10 seconds (see Quality Attributes) - showing exact seconds would claim a precision the polling model doesn't actually have, and the number would visibly lag reality between polls regardless of how finely it's formatted.

The elapsed figure itself has no ready-made source on the engine's current read surface. Node.as_dict() (what lc show/lc claim expose, pinned by TestNodeDTOReadSurface) carries since and fired_at, but neither is set automatically when a step goes active - both are only written when something explicitly calls update_metadata. The one place a step's claim moment is recorded automatically is the store's internal history table (every state transition logged by_record_history, including the in_progress transition inside claim_ready), and the domain's only existing consumer of that history - Duration.elapsed() - measures claim-to-done and returns None while a step is still active, with no path for a still-running elapsed time. Getting from that history table to a live-updating figure on the dashboard is unbuilt plumbing this story depends on, not something the engine already surfaces.
