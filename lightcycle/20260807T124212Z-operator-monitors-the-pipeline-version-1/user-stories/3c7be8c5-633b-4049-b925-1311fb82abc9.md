## Scroll the list with arrow keys

**Who:** Operator

**What:** Arrow keys move a selection cursor through the full list.

**Why:** Keyboard-only navigation, matching a terminal-native tool.

**Activity:** Get oriented on the pipeline - See the whole pipeline at a glance - what's active, blocked, waiting on me, and queued - the moment it changes, as long as the dashboard is running.

**Step:** Review current work status

**Status:** ready

### Acceptance Criteria

- Given the list has more rows than fit on screen, when I press up/down, then the selection moves to the previous/next row, scrolling as needed.
- Given the selection is at the first or last row, when I press past the end, then it stays put rather than wrapping.
- Given the list is longer than one screen, when I press Ctrl+U or Ctrl+D, then the view jumps by roughly a full screen at a time.

### Context

The design's Quality Attributes doc flags an open question that lands squarely on this story: how the priority list should behave once the live store holds substantially more than today's real counts (250 items) isn't specified anywhere in this design - not in the architecture doc, not in any story. Arrow-key and Ctrl+U/Ctrl+D scrolling is the exact mechanism that question is about, so this story's build shouldn't assume the wireframe's short example list generalizes to a much longer one; degradation behaviour at scale is unresolved, not implicitly "whatever the widget does by default."
