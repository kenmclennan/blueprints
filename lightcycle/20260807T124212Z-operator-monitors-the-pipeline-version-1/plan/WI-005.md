## WI-005: Elapsed-time-since-claim computation

**Brief:** Nothing in the engine's current read surface produces a live "how long has this been running"
figure for an active step. `Node.since`/`fired_at` exist but aren't set automatically when a step goes
active. The one durable record of a claim moment is the store's internal history table (written by
`claim_ready`), and the domain's only existing consumer of it - `Duration.elapsed()` - measures
claim-to-done and returns `None` while a step is still active. This item builds the missing path: from
that history table to a live-updating elapsed figure a use case can expose.

### Acceptance Criteria

Restated in Given/When/Then form from the two stories that both depend on this figure existing
(Priority List's WI-012 and the hub header's WI-027):

- Given a step is `in_progress`, when the new computation runs, then it returns the elapsed duration from
  that step's first `in_progress` history timestamp to now.
- Given a step has not yet gone `in_progress`, when the new computation runs for it, then it returns no
  elapsed value (there is nothing to measure yet) - it must not reuse `Duration.elapsed()` as-is, since
  that returns `None` for exactly the still-active case this item needs a value for.
- Given the poll loop re-renders, when elapsed time is displayed, then the value is approximate (matching
  the 10-second poll interval), never claiming false precision to the second.

### Dependencies

None.

### Constraints

- Confirmed against live code (2026-08-11): `_record_history` (`sqlite_store.py`) is called by
  `claim_ready` on the `in_progress` transition - the timestamp this item reads exists and is durable.
  `Duration.elapsed()` (`domain/feedback/duration.py`) confirmed to require both a first `IN_PROGRESS`
  and a last `DONE` timestamp, returning `None` if either is missing - confirmed this item cannot reuse
  it unmodified for a still-running step.
- Format convention (from the design, not invented here): approximate values like `14m`, `45s`,
  `1h 7m` - see WI-012's own Acceptance Criteria for the exact rendering this feeds.

### Verification

- Unit test: an active step's elapsed value is computed correctly from a fake history fixture.
- Unit test: a not-yet-active step returns no elapsed value.
- Unit test: `Duration.elapsed()`'s existing claim-to-done behavior is unmodified (regression).

### Open Questions

- `[builder]` Whether elapsed time is computed once per poll tick inside a use case, or computed
  client-side in the TUI from raw timestamps - the API Contracts artifact states this explicitly as
  undecided, both options defensible.

### Deliverable

A computation (use-case-layer or TUI-layer, per the open question above) that returns a live elapsed
duration for an `in_progress` step from the store's history table, unit-tested, with no false precision
claimed.
