## WI-006: Blocking-dependency-id resolution on the live read path

**Brief:** Every live read path that hydrates a `Node` (list, single-item detail, hierarchy) only ever
carries `deps` as a bare unresolved-blocker count, never the blocking node's own id. The one place the
engine resolves actual blocker ids is `export_rows`, a separate full-store dump - not part of normal node
hydration. Three downstream stories (Priority List's dependency indicator, the hub's "why escalated", and
the hierarchy's dependency marker) all need a specific blocking id on the live path.

### Acceptance Criteria

Restated in Given/When/Then form from the three stories that independently hit this gap:

- Given a node has one or more unresolved dependencies, when it's hydrated on the live read path (list,
  single-node, or hierarchy), then at least one blocking node's own id is available to render, not just a
  count.
- Given a node has more than one unresolved dependency at once, when it's hydrated, then the read model
  does not assume there is exactly one candidate - the wireframes' single-id display format (e.g.
  "blocked · LC-54.4") is a display choice building on top of this data, not a constraint this item's own
  data shape should impose.
- Given the change is in place, when existing consumers of `Node.deps` as a bare count run (anything not
  touched by this item), then their behavior is unchanged - this is an additive field, not a
  replacement of `deps: int`.

### Dependencies

None.

### Constraints

- Confirmed against live code (2026-08-11): `_rows_to_nodes` (`sqlite_store.py`) builds `deps_by_id` via
  a `COUNT(*)` grouped query - confirmed count-only. `export_rows` runs a separate per-node
  `SELECT blocked_by FROM deps WHERE node_id = ?` and includes actual `blocked_by` ids - confirmed this
  is the only existing id-resolving path, and it is not part of `get_node`/`node_view`/hierarchy
  hydration.
- Must not remove or change the meaning of `Node.deps: int` (the existing count) - this item adds
  blocker-id resolution alongside it, not instead of it.

### Verification

- Unit test: a node with one unresolved dependency exposes that dependency's id via the extended read
  path.
- Unit test: a node with multiple unresolved dependencies exposes more than one id (data shape does not
  silently drop to one).
- Regression: `Node.deps` count-only consumers unaffected.

### Open Questions

- `[builder]` Whether this becomes a new field on `Node` (e.g. a list of blocker ids alongside the
  existing count), a separate query the read-model layer joins in, or a switch to reusing `export_rows`'
  per-node query pattern on the live path - not specified by the design.

### Deliverable

The live node read path (list, single-node, hierarchy) exposes at least the blocking node's id for any
unresolved dependency, unit-tested, without altering `Node.deps`'s existing count semantics.
