# WI-006 - Log tab

## What

The hub's Log tab fills in: a live tail for a running step, the historical log for a finished one, and an explicit state for a step that has no log to show.

## Defined by

- [wireframe-hub.html](../wireframes/wireframe-hub.md) - the Log tab's rendering in each of its states, including the no-log state and how the transition to finished is presented.
- [TUI Architecture](../architecture/tui-architecture.md) - that this tab tails a file offset directly and bypasses the poll loop, and the widget selected for it. The bypass is a design decision, not an optimisation to decide at build time.
- [Quality Attributes](../quality-attributes/quality-attributes.md) - that live log latency is deliberately unbounded and tied to file writes, which is a consequence of that same bypass.
- [Keyboard Navigation Scheme](../design-system/keyboard-navigation-scheme.md) - scrolling and fast-scrolling within a long log, and back-navigation.
- The stories this item delivers:
  - [See the live log tail as it's written](../user-stories/28a501f3-8018-418b-b0f0-f068a928eb2c.md)
  - [See that a step has no live log to stream](../user-stories/8ff7f352-1a1b-4f3f-b557-2a5cd164a8ff.md)
  - [Scroll back through the live buffer](../user-stories/36a4fe94-2feb-4b79-a740-6a18fa6893c1.md)
  - [See when the step finishes while I'm watching](../user-stories/a0a38358-9b11-4966-abd8-17edf7fd5987.md)
  - [Return to the node without losing position](../user-stories/2f58b727-2ff9-4f23-b2d5-96e4c1b63d19.md)
  - [See a done step's historical log](../user-stories/3c609f13-cc69-4772-92a3-e2966d4a234e.md)

## In scope

- Live tailing by offset, the historical read for a done step, and the no-log state.
- Scrolling back through the buffer, including fast-scroll.
- Rendering the step finishing while it is being watched.
- Back-navigation to the node, restoring position.

## Out of scope

- The hub shell and tab cycling - WI-005.
- The Artifacts tab - WI-007.

## Done when

The acceptance criteria on all six stories hold.

## Notes from the codebase

`ResolveLogUseCase` (`lightcycle/application/pool/resolve_log.py`) resolves a step's log path durably, and `TraceNode` already carries `log` - both covered by non-`@wip` feature files, so locating the file is not part of this item. The tailing itself has no existing implementation.

`worker_log_filename` in `lightcycle/domain/work/` is the naming rule those paths follow, if a builder needs to reason about which file belongs to which step.

Where the design and the codebase disagree, the design wins.

## Open questions

- `[builder]` Whether the tail is polled at its own cadence or driven by filesystem notification. The design states only that it is independent of the screen's poll interval and that latency follows file writes.
- `[designer]` The design does not state a buffer bound for a very long-running step's log. [Quality Attributes](../quality-attributes/quality-attributes.md) records an equivalent open question about behaviour under a large store; this is the same question for logs.
