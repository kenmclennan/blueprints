## WI-001: `Artifact` gains `internal` and `kind` fields

**Brief:** Add two fields to the engine's `Artifact` record - `internal` (boolean) and `kind` (string) -
both set only at the point of attachment, never inferred at read time. This is Change 1 in the
Architecture artifact, explicitly declared as part of this design's own delivery, not a prerequisite
filed elsewhere. Nearly every Milestone 2/3 work item depends on it.

### Acceptance Criteria

Derived directly from the mandated behavior in the Source Reference below (this is an engine-foundation
item with no authoring story, so criteria are restated in Given/When/Then form from the architecture
text itself, not paraphrased):

- Given an artifact is attached with `kind` explicitly declared at the point of attachment, when it's
  persisted, then that declared kind is stored as given - this is the override and extension point.
- Given an artifact is attached with no `kind` declared, when its `type` is `pr`, then `kind` defaults to
  `url`.
- Given an artifact is attached with no `kind` declared, when its `type` is `spec` or `brief`, then
  `kind` defaults to `filepath`.
- Given an artifact is attached with no `kind` declared, when its `type` is `repo` or `branch`, then
  `kind` defaults to `text`.
- Given an artifact is attached with no `kind` declared and a `type` outside that table, when it's
  persisted, then `kind` defaults to `text`.
- Given an artifact is attached at one of these existing write points - `application/feedback/reflect.py`
  (type `reflection`), `application/work/resolve_backlog.py` (types `resolved-by`/`resolves`),
  `application/pool/monitor_prs.py` (types `watched-step`/`feedback-spawned-through`), or the
  feedback-handling step's `lc attach --replace` call setting `feedback-watermark` - when it's persisted,
  then `internal` is set `true`. Every other write point sets `internal` `false`.
- Given `internal` or `kind` is read back anywhere (hierarchy content indicator, Artifacts tab filter,
  viewer dispatch), when it's read, then the value is never inferred from the artifact's `value` shape
  (e.g. whether it looks like JSON) - both fields stay a total function of what was set at attach time,
  since a future workflow may legitimately attach real JSON content under any type.

### Dependencies

None - this is the first item in the plan.

### Constraints

- Also a Domain Model change (`domain-model/domain-model.md` notes this without restating it - the
  architecture doc's field-level detail is authoritative, this item builds against that, not a second
  copy).
- `type` vocabulary itself stays free-form; only the `kind` defaulting table changes.
- Confirmed against live code (2026-08-11): `lightcycle/domain/work/artifact.py`'s `Artifact` is
  currently exactly `(type: str, value: str, label: Optional[str] = None)` - no `internal`, no `kind`.
  `application/work/link_artifact.py`'s `LinkArtifactInput` is currently `(item, atype, value, label,
  replace: bool = False)` - no `kind`/`internal` parameter yet, confirming this is real, unbuilt work,
  not already-landed engine surface.

### Verification

- Unit tests on the `Artifact` dataclass covering both new fields' defaults and explicit-value paths.
- Unit tests on the attach-time resolution order (explicit → type-table → `text` fallback) for every
  type in the table, plus at least one type outside it.
- Unit tests confirming each of the four internal write points sets `internal=true` and every other
  existing call site sets `internal=false`.
- Existing `tests/unit` artifact/link_artifact test suites extended, not replaced.

### Open Questions

- `[builder]` Exact persistence mechanism for the two new fields (new sqlite columns on the artifacts
  table vs. an encoded value) - not specified by the design, a build-time schema choice.
- `[builder]` Whether `--kind`/`--internal` become new CLI flags on `lc attach`, or stay internal-only
  parameters wired directly at the four bookkeeping write points (which never go through the CLI attach
  path) plus a `LinkArtifactInput` field for everything else.

### Deliverable

`Artifact.internal: bool` and `Artifact.kind: str` exist on the domain record, correctly populated at
every existing write point per the rules above, with the attach-time resolution order implemented and
unit-tested. No TUI code depends on this yet - it lands as pure engine surface.
