# WI-001 - Shared visual vocabulary and screen chrome

## What

The dashboard renders inside the design's own frame, and the shared visual vocabulary every screen draws from exists as one citable thing in the code rather than being re-derived per screen.

## Defined by

- [Design System Tokens](../design-system/design-system-tokens.md) - the colour tokens, the state-to-glyph-and-colour table, the per-screen column grids, the typography stack, and the footer's structure. This is the whole substance of the item; build the vocabulary to match it exactly, including which token is deliberately absent from which screen.
- [Keyboard Navigation Scheme](../design-system/keyboard-navigation-scheme.md) - which keys the footer's shortcut line advertises, and the global set that appears on every screen.
- [wireframe-priority-list.html](../wireframes/wireframe-priority-list.md) - the frame, tab strip and footer as rendered. The `#normal` state is the reference for chrome; its rows belong to WI-002.
- [See a contextual shortcut bar in the footer](../user-stories/75374a1f-589b-421e-b5be-2191407b5d9a.md) - the acceptance criteria.
- [Quality Attributes](../quality-attributes/quality-attributes.md) - the standing rule that no state is signalled by colour alone, which is why the vocabulary pairs glyph with colour rather than defining colours on their own.
- [Terminal-Native, No Server](../principles/terminal-native-no-server.md) - why the chrome is drawn in the terminal rather than delegated to anything else.

## In scope

- The shared vocabulary as a real module the other screens import: state to glyph and colour, the column grids, the colour tokens.
- The bordered frame, the tab strip, and the two-line footer structure on the screen that exists today.
- The footer's contextual shortcut line, and how its content is supplied per screen.

## Out of scope

- Any row rendering inside the priority list - WI-002.
- The footer's status-line segments beyond what already renders (version, upgrade, claude availability) - WI-003.
- The backlog's own chrome differences - WI-004.
- The hub's tab strip and header - WI-005.

## Done when

The scenarios in `tests/feature/dashboard-adopts-the-design-system.feature` pass with their `@wip` tags removed, and the acceptance criteria on the story above hold.

## Notes from the codebase

At `b2aa7b6` the TUI is a single module, `lightcycle/adapters/tui/app.py`, holding `LightcycleApp` and a one-line `StatusBar` docked bottom. There is no tokens or vocabulary module - nothing in `lightcycle/adapters/tui/` other than `app.py` and an empty `__init__.py`. The frozen scenarios for this item already exist in `tests/feature/dashboard-adopts-the-design-system.feature`, entirely `@wip`.

`CLAUDE.md` already permits `textual` as a normal dependency for this adapter and already describes `adapters/` as covering driving adapters, so neither rule needs changing. `pyproject.toml` declares `textual`, and `lc tui` is wired at `cli.py:903`.

`tests/support/tui_harness.py` exists and is how a TUI scenario binds, per `CLAUDE.md`'s own testing rule.

Where the design and the codebase disagree, the design wins.

## Open questions

- `[builder]` Whether the vocabulary is a plain module of constants or Textual CSS variables, or both. The design states the values; how they reach a widget is a build-time choice.
- `[designer]` The tab strip is specified for the two top-level screens, but the design does not state whether it stays visible inside an open node or is replaced by the hub's own tab strip. [wireframe-hub.html](../wireframes/wireframe-hub.md) is the artifact that would settle it.
