# WI-016 - Node hub header and hierarchy fidelity

## What

Filed by `audit-design` against the built Node Hub, not by a story - three gaps found by rendering the real composited screen and reading `hub.py` against `wireframe-hub.html`, none of them the already-filed LC-273/275/277/282/284/289 or the already-delivered WI-009/WI-011.

## Reproduced

All three against `origin/main` at `13694fc` via `tests/support/tui_harness.py` reading the actual composited frame.

1. **Header field values render in `--dim`, not `--text`, losing the key/value contrast the wireframe specifies.** [wireframe-hub.html](../wireframes/wireframe-hub.html)'s `.fieldset .field` CSS is explicit: `.field .k { color: var(--dim); }` / `.field .v { color: var(--text); }` - the STEP/ROLE/ELAPSED/STATE labels are dim but their values are full-brightness `--text`, distinct from the meta-rows (project/theme/workflow/description), which the wireframe and the build both correctly render uniformly dim. `HubHeader._line()` (`hub.py`) instead renders each whole `"STEP: write-code"` string - key and value together - as one `Text(..., style=COLOURS["dim"])`. `uv run python -m tests.support.screen_render hub#step-node --colour` confirms every field line comes back as a single dim RGB run; no segment is ever `--text`. This is the visual treatment behind [See the item's current step, role, and elapsed time](../user-stories/45d7d629-f736-4875-8470-f928558a88ea.md). No test checks style/colour here - `tests/feature/test_the_node_hub.py` asserts only the literal string, so the mismatch regresses silently.
2. **A theme's own hub header never shows the wireframe's "theme · N items underneath" line, and cannot show a project line either.** [wireframe-hub.html](../wireframes/wireframe-hub.html)'s `#theme` state gives a theme opened as its own node two meta-rows: `project: lightcycle` and `theme · 4 items underneath`. `build_header()`'s theme branch (`hub.py`) has no field anywhere in `HeaderData` for an item-count line, and `uv run python -m tests.support.screen_render hub#theme` shows no meta-rows at all - not even the project line, despite the fixture registering one. The project line's absence is structural, not incidental: `project_of()` (`lightcycle/application/work/project_of.py`) derives project solely from a `repo` artifact attached to the queried node itself, and per [Ontology](../glossary/ontology.md) an artifact is attached to an item, never a theme - so the wireframe's theme-state `project:` line can never render for any theme in the real system, not just this fixture.
3. **The `l` jump-to-log key silently no-ops on a fully-done item or theme, contradicting the documented "past/historical if done" behaviour.** [Keyboard Navigation Scheme](../design-system/keyboard-navigation-scheme.md)'s Hierarchy tab table states `l` is "live if it's the active step, past/historical if done. No-op on a human step or a step that hasn't run" - the no-op carve-out is scoped to a human/not-yet-run step, not to item/theme rows. `HierarchyPagingTable.action_jump_log()` (`hub.py`) branches: a `step` row correctly uses `log_tab_mode()`, which returns `"historical"` when done and jumps to the Log tab; an `item`/`theme` row instead calls `current_step()`, which returns `None` once every child is done, and the action no-ops with nothing else attempted - there is no fallback to the item's last completed step for a historical view. Reproduced: a theme → item with every step `done` - highlighting the item row and pressing `l` leaves the screen unchanged; highlighting one of its done steps directly and pressing `l` correctly opens the Log tab. The identical "done, has a real log" case behaves differently depending only on which row is highlighted.

## Defined by

- [wireframe-hub.html](../wireframes/wireframe-hub.html) - the `.fieldset .field` key/value colour rule (point 1) and the `#theme` state's meta-rows (point 2).
- [Ontology](../glossary/ontology.md) - artifacts attach to items, not themes, which is why point 2's project line is a structural gap.
- [Keyboard Navigation Scheme](../design-system/keyboard-navigation-scheme.md) - the `l` key's documented behaviour (point 3).
- [See the item's current step, role, and elapsed time](../user-stories/45d7d629-f736-4875-8470-f928558a88ea.md), [Jump straight to a node's artifacts or log from the hierarchy](../user-stories/8f6e008e-f9d8-4c6d-a061-02da7002bd42.md).

## In scope

- Splitting header field lines into a dim key and a `--text` value, matching the wireframe.
- Either adding a theme item-count line and resolving what a theme's "project" should show (see Open questions - this may be a design question, not purely a build one), or, if the design's own `#theme` state is judged wrong given artifacts only attach to items, correcting the design artifact instead.
- Giving `l` a fallback to an item/theme's last completed step when every child is done, consistent with what `Enter` and the step-row case already do.

## Out of scope

- Anything already delivered by WI-009 (hierarchy tree background, pinned-ancestor icon, escalation panel, `l` on a row with a *live* current step) or WI-011 (live log cursor cue).
- The row-grid column overflow issues (WI-008) and stacked-row rendering (WI-013).

## Done when

Header field values render at `--text` against dim keys; a theme's own hub header either shows an item-count line and a project value the design can actually source, or the Blueprint's `#theme` state is corrected to match what a theme can structurally carry; and `l` opens the Log tab for a done item/theme exactly as it does for a done step, in the same historical mode - each verified on the actual composited frame.

## Open questions

- `[designer]` Whether a theme's header is meant to show a project at all, given [Ontology](../glossary/ontology.md) attaches artifacts (and so `repo`) only to items, not themes - `wireframe-hub.html#theme`'s `project: lightcycle` line may need to be dropped from the design rather than built, unless a different derivation (e.g. from the theme's own items) is intended.
