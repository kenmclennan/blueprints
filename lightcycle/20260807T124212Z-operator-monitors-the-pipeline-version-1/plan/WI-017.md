## WI-017: See a dependency indicator on blocked items

**Brief:** On the priority list's needs-attention group, distinguish an item blocked on another item's
completion (dependency) from one blocked for another reason (e.g. escalated step), via a dual icon plus
the blocking item's id shown inline.

### Acceptance Criteria

Copied verbatim from the source story:

- Given an item is blocked specifically because it depends on another item's completion, when it appears
  in the priority list, then it shows a dependency icon alongside its usual needs-attention marker (not
  instead of it), plus the blocking item's id shown inline (e.g. 'blocked · LC-54.4').
- Given an item is blocked for a reason other than a dependency (e.g. an escalated step), when it appears
  in the list, then no dependency indicator is shown.

### Dependencies

- WI-011, WI-006 (blocking-dependency-id resolution).

### Constraints

- Blocking id sourced from WI-006's extended read path - this item does not resolve blocker ids itself.
- Per WI-006's own note: a node can have more than one unresolved dependency; this item's display (one
  id inline) is a display choice built on WI-006's data, which may carry more than one candidate - pick
  one deterministically (e.g. first by id) since the wireframe shows only a single-id format.

### Verification

- Pilot test: a needs-attention fixture item with a resolved blocking dependency shows the dual icon plus
  the blocking id inline.
- Pilot test: a needs-attention fixture item blocked for a non-dependency reason shows the single
  needs-attention icon only, no dependency indicator.

### Open Questions

- `[builder]` Deterministic tie-break when a node has more than one unresolved dependency (e.g. lowest
  id, earliest-created) - not specified by the design.

### Deliverable

Dependency-blocked needs-attention items show the dual icon and blocking id; non-dependency
needs-attention items don't.
