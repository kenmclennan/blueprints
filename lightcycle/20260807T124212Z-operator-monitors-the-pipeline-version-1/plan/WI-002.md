## WI-002: Read-only pool-running-state use case

**Brief:** Add a read-only use case that answers "is `lc start`'s pool currently running" without
mutating anything. The only existing way to answer this today is `AcquireRunLockUseCase`, which actually
attempts to claim `.lc-run.pid` - calling it from the TUI would seize the lock itself whenever the pool
is down, blocking the real `lc start` from acquiring it. This violates the "Observation Only" principle
and must not be reused as-is.

### Acceptance Criteria

Restated in Given/When/Then form from the story context this gap was found in (no dedicated story owns
this engine gap directly - it surfaced inside "See whether the pool is running"'s own Context field):

- Given `.lc-run.pid` exists and its recorded pid is alive, when the new use case is called, then it
  reports the pool as running, without writing to or removing `.lc-run.pid`.
- Given `.lc-run.pid` does not exist, or exists but its recorded pid is dead, when the new use case is
  called, then it reports the pool as not running, without creating, writing to, or removing
  `.lc-run.pid`.
- Given the use case is called any number of times in a row, when compared to a real `lc start`
  attempting to acquire the lock afterward, then the real acquire's outcome is unaffected - the read path
  never competes for or holds the lock.

### Dependencies

None.

### Constraints

- Confirmed against live code (2026-08-11): `AcquireRunLockUseCase.execute()`
  (`application/pool/run_lock.py`) calls `self._lock.acquire()`, which does
  `os.open(path, O_CREAT|O_EXCL|O_WRONLY)` - genuinely mutating, confirmed no existing read-only
  equivalent (`RunLockPort` exposes only `acquire()`/`release()`).
  `pid_alive(pid)` (`adapters/workers.py`) is a bare `os.kill(pid, 0)` liveness check with no start-time
  verification (a PID-reuse edge case exists in principle) - this item reuses that exact existing check,
  it does not need to build the more robust `worker_alive`/`process_start_time` combination that also
  exists in the same file for a different purpose.
- Must not touch `RunLockPort.acquire()`/`release()` - this is an additive read path only.

### Verification

- Unit test: pool running (pid alive) reports true.
- Unit test: no pidfile reports false.
- Unit test: stale pidfile (pid dead) reports false.
- Integration test: calling the new use case any number of times does not prevent a subsequent real
  `AcquireRunLockUseCase.execute()` from succeeding.

A new read-only use case (exact name/module a build-time choice) that reports pool-running state without
