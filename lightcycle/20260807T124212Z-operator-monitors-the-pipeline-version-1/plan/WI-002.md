# WI-002 - Priority list renders current work

## What

The landing screen becomes the priority list the design specifies: needs-attention, active and queued as three fixed-order groups, each row carrying the fields the grid defines, with the bell ringing on entry to needs-attention.

- [Design System Tokens](../design-system/design-system-tokens.md) - the state-to-glyph-and-colour table and this screen's column grid, consumed from WI-001's module rather than re-derived.
- [Domain Model](../domain-model/domain-model.md) - what needs-attention is and which engine lanes it merges. The merge is a design decision, not an implementation shortcut, and the artifact also names the engine field that must not be used as its source.

## In scope

- Group ordering, separators, per-group glyph and colour, and the empty state.
- Every column the grid defines, including the project and step columns.
- Elapsed time for active rows, including a formatter that covers the wireframe's full ladder. This is the one piece other screens reuse, so it lands somewhere they can reach.
- Selection movement, selection persistence across polls, and the dependency indicator.
- The needs-attention bell.

## Out of scope

- The frame, tab strip and footer chrome - WI-001.
- Footer status-line content - WI-003.
- Opening a row into the hub - WI-005 owns the hub; this item leaves rows selectable but not openable.
- The backlog's own rows, which use a different grid - WI-004.

## Done when

The three groups render in fixed order with their own glyphs and colours against the wireframe, and the acceptance criteria on all nine stories hold.

## Notes from the codebase

At `b2aa7b6` the landing screen renders a `DataTable` fed by `QueueUseCase`, with column headers and the columns in engine order. Both the widget choice and the data source are wrong against this design: the queue lane is one of the three groups, not the whole list, and the design's grid has neither headers nor that column order. Treat the existing table as scaffolding to replace, not a starting shape to extend.

Scenarios for this item were written ahead of the code and sit unimplemented in `tests/feature/priority-list-renders-current-work.feature`, with no step definitions bound yet - read them first, they are more specific than this item's prose. The engine reads this item needs all exist and are locked by feature tests:

- Lanes come from `StatusUseCase` (`lightcycle/application/work/status.py`), which returns all four raw lanes; the merge into needs-attention has no engine equivalent and happens here.
- `Node.blocked_by` carries the blocking ids the dependency indicator needs.
- `Duration.elapsed_since_claim(now)` (`lightcycle/domain/feedback/duration.py`) returns a `timedelta` from a step's first `IN_PROGRESS` transition. A formatter already exists but is private to another layer and covers only part of the wireframe's ladder: `_fmt_duration` at `lightcycle/cli.py:1417`. Extend and relocate it, or decide deliberately to keep it separate - do not write a second one.
- `project_of(store, item)` (`lightcycle/application/work/project_of.py`) already returns the short label the rows show, not an identity needing further resolution: it reads the item's `repo` artifact, and `backlog-counts.feature` pins that behaviour. **The design says otherwise** - [API Contracts](../api-contracts/api-contracts.md) describes this value as needing resolution to a display name. That claim has aged; no derivation is needed, here or in WI-004 and WI-005. (`Node.project` is a different field and not what the rows read.)
- `PlannedStepsUseCase` supplies a queued step's next step name.

Where the design and the codebase disagree, the design wins.

## Open questions

- `[builder]` Whether `DataTable`, a custom `ListView`, or hand-rendered rows can honour the column grid exactly. The grid is not negotiable; the widget is. A widget whose native rendering fights the grid is the wrong widget, not a reason to move the grid.
- `[builder]` Whether the elapsed formatter lives in the use-case layer, the domain, or the adapter. [API Contracts](../api-contracts/api-contracts.md) states the trade-off and asks for it to be decided deliberately; any answer is acceptable so long as it lands in one place WI-004 and WI-005 can reuse.
