## WI-031: Hierarchy: node id/state/role/dependency indicator

**Brief:** Populate each hierarchy row with its real id, state (reusing the exact labels/icons/colours
the priority list already uses), role for step nodes performed or being performed by a worker, and a
dependency indicator distinct from other blocked reasons - live-updating.

### Acceptance Criteria

Copied verbatim from the source story:

- Given a node in the hierarchy, when it renders, then its own real id (e.g. LC-143.3.4) is shown
  alongside its title, and its current state is shown using the same labels/icons/colours as the priority
  list.
- Given a node's state changes while the hierarchy is open, when that happens, then it updates without a
  manual refresh.
- Given a step node has been performed, or is being performed, by a worker, when it renders in the
  hierarchy, then its role (e.g. write-code, review-code) is shown alongside its state.
- Given a step node is a human step, when it renders, then no role is shown for a worker that doesn't
  exist.
- Given a node is blocked on another item's completion, when it renders in the hierarchy, then a
  dependency indicator is shown alongside its state, distinct from other blocked reasons.

### Dependencies

- WI-030, WI-004 (role on the read path), WI-006 (blocking-dependency-id resolution, needed to know
  *whether* a node is blocked by dependency at all, even though this row-level indicator does not need
  the specific blocker id the way WI-017/WI-038 do), WI-055 (planned-step rows, which this item's own
  state/role rendering rules must not silently break on).

### Constraints

- **Role rendering shows the literal string `"human"`**, not an empty slot, matching WI-027's own AC-4
  discipline - the same value-comparison rule applies here.
- State icon/colour/label vocabulary must be identical to WI-011/012/013's Priority List implementation -
  do not re-derive a second copy of the state-to-icon mapping.
- Live-updates via the same poll loop already established (WI-010), applied to the hierarchy's own
  render, not a separate mechanism.
- **This story's own AC-1/AC-3 ("its current state," "has been performed, or is being performed") only
  apply to real, filed nodes** - a WI-055-projected planned row has no real `state`/`role` to read (it
  isn't a `Node` row at all). No design-system token exists for a "planned, not yet filed" visual state
  (see WI-055's own Open Questions) - render it distinctly from a real queued step rather than reusing the
  plain queued `○` literally, even though the wireframe's own example does exactly that; flag this
  divergence rather than ship a row an operator cannot tell apart from a real, actionable one.

### Open Questions

- `[designer]` Same open question as WI-055's own: no design-system token exists for a planned-but-
  unfiled row, and the cited wireframe visually reuses the plain queued icon for it. This item cannot
  resolve that gap on its own; it's recorded here too since this is the item that would otherwise silently
  ship the ambiguous treatment.

### Verification

- Pilot test: every state (needs-attention, active, queued, done, blocked-by-dependency) renders with the
  same icon/colour as its Priority List equivalent, for a hierarchy fixture.
- Pilot test: a worker-role step shows its role; a human step shows the literal "human" text, not blank.
- Pilot test: a node blocked by another item's completion shows the dependency indicator, distinct from a
  node blocked for another reason.
- Pilot test: simulating a state change across two poll ticks updates the row without manual refresh.

### Deliverable

Every hierarchy row shows correct id, state, role, and dependency indicator, reusing the Priority List's
exact visual vocabulary and updating live.
