# WI-015 - Backlog filter bar never renders

## What

Filed by `audit-design`, not by a story - the backlog screen's filter bar (`PROJECT: <name>` on the left, `N items` on the right) never reaches the composited frame on any backlog state. The row where it belongs renders as blank space.

## Reproduced

Verified against `origin/main` at `13694fc` via `tests/support/tui_harness.py` reading the actual composited frame, on `backlog#normal`, `#empty`, `#empty-filtered`, `#claude-unavailable` and `#stacked` alike (`uv run python -m tests.support.screen_render backlog#normal --colour`, also at `--size 140x40`):

```
│Current work · Backlog                                                                            │
│──────────────────────────────────────────────────────────────────────────────────────────────────│
│                                                                                                  │   <- filter bar row: blank
│ ❯   LC-273  lightcycle  Row title repeats the step name                                          │
```

**Root cause**: `#backlog-filter-bar`'s CSS in `lightcycle/adapters/tui/app.py` gives the `Horizontal` container `height: 1; border-bottom: solid ...`. Under Textual's border-box sizing, the border-bottom line consumes the container's entire single allocated row, leaving `container_size.height == 0` even though `region.height == 1` - confirmed directly by inspecting the mounted widget. The child `Static("PROJECT: All")` and `Static("13 items")` are correctly updated by `_render_filter_bar` with the right text and style; they simply have zero rows to paint into, so nothing reaches the compositor. Reading the raw compositor strip at that row shows an unstyled fallback fill, not actual widget output.

**Why existing tests pass anyway**: `tests/feature/test_the_backlog_screen.py`'s `_rendered_text()` helper calls `widget.render_line(0)` directly on `#backlog-filter-left`/`#backlog-filter-right` - which correctly returns the right strings even though the container positioning those widgets never actually composites them onto the screen. Both of `the-backlog-screen.feature`'s filter-bar scenarios pass today because neither reads the actual composited frame.

## Defined by

- [wireframe-backlog.html](../wireframes/wireframe-backlog.html) - the `.filterbar` block, present in every state (`#normal`, `#picker-open`, `#empty`, `#empty-filtered`, `#claude-unavailable`).
- [Filter the backlog by project](../user-stories/b4b5ce79-8c4b-4fb4-a4c9-1a040e4c6bb7.md) - AC-4, that the filter bar shows the current filter's own item count.
- [See a quiet message when the backlog is empty](../user-stories/addfdbfd-a67a-43f5-a343-dd2f45af15ff.md) - both empty-state wireframes include the filter bar above the empty message.

## In scope

- Fixing `#backlog-filter-bar`'s sizing so its content row survives alongside its border line (e.g. `height: 2` for border-box sizing, or switching to `box-sizing: content-box`), so `PROJECT: <name>` and the item count actually reach the compositor.
- A compositor-level test assertion (reading the actual composited frame, not `render_line` on the child widgets directly) so this can't silently regress again.

## Out of scope

- The filter bar's content or logic - `_render_filter_bar`'s text and counts are already correct; only their reaching the screen is broken.
- The picker itself, already delivered and correct (WI-004, WI-012).

## Done when

`PROJECT: <name>` and the item count render visibly on the backlog screen's filter bar row, on every backlog state, verified by reading the actual composited frame rather than a widget's own `render_line` report.
