# WI-014 - Priority List rows paint a non-token background colour

## What

Filed by `audit-design`, not by a story - every non-cursor row in the Priority List's `PriorityTable` paints Textual's own default DataTable surface colour instead of `--bg`, a colour absent from the design system's token table entirely.

## Reproduced

Verified against `origin/main` at `13694fc` via `tests/support/tui_harness.py` reading the actual composited frame's `bgcolor` (not foreground - the render tool's own `--colour` row extractor only reads foreground colour, which is why this was invisible to it). Extracting `bgcolor` from `session.app.screen._compositor.render_strips()` on `priority-list#normal`:

```
(3, '#1c2a2c') 98   <- cursor row, correct (--selected-bg)
(4, '#272727') 98   <- gap row
(5, '#272727') 98   <- active row
(6, '#272727') 98   <- gap row
(7, '#272727') 98   <- queued row
(8, '#272727') 98   <- queued row
(9, '#272727') 98   <- queued row
```

Every row except the one under the cursor paints `#272727` - not `--bg` (`#0c0c0f`) and not any value in [Design System Tokens](../design-system/design-system-tokens.md)'s colour table at all. `lightcycle/adapters/tui/app.py`'s `LightcycleApp.CSS` sets `Screen { background: --bg }` and `DataTable > .datatable--cursor { background: --selected-bg }`, but gives `PriorityTable` (or `DataTable` generally) no `--bg` background rule of its own, so Textual's built-in default shows through everywhere except the cursor row. Reproduced identically on `priority-list#claude-unavailable`. The rows above/below the table (tab strip, padding, footer) correctly paint `#0c0c0f`, so the mismatch is confined to exactly the list's row area - a visibly distinct grey panel floating behind almost the entire screen, which the design never specifies.

This is the same bug class as WI-009's already-delivered finding on the Hub's `HierarchyPagingTable`, but this instance is in the Priority List's own `PriorityTable` and was out of that item's scope.

No test guards against it: `tests/feature/test_priority_list_renders_current_work.py`'s `test_a_selected_rows_own_state_colour_survives_rendering` asserts the cursor row's background equals `--selected-bg`, then for a deselected row asserts only `bgcolor != COLOURS["selected-bg"]` - never that it equals `--bg`. `#272727` satisfies that inequality, so the defect passes silently.

## Defined by

- [Design System Tokens](../design-system/design-system-tokens.md) - the colour token table: only `--bg` and `--selected-bg` are valid backgrounds inside the terminal frame.
- [wireframe-priority-list.html](../wireframes/wireframe-priority-list.html) - `.row.selected { background: var(--selected-bg); }` is the only background rule any row carries; every other row inherits `.term`'s `--bg`.

## In scope

- Giving `PriorityTable` (or `DataTable` generally, if shared with other screens' own already-correct rows) an explicit `--bg` background so no row paints Textual's default surface colour.
- A compositor-level (not widget-self-report) test assertion that an unselected row's background equals `--bg` exactly, closing the loophole the existing inequality assertion leaves open.

## Out of scope

- Any other colour or glyph treatment already covered by WI-001/WI-002/WI-009/WI-011.

## Done when

Every non-cursor row in the Priority List paints `--bg`, verified by reading the actual composited frame's `bgcolor` (not a widget's own `render_line` or `styles.background`), on both `priority-list#normal` and `priority-list#claude-unavailable`.
