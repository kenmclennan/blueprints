## WI-013: Queued items at the bottom

**Brief:** Group ready-but-unclaimed, non-human steps at the bottom of the priority list, moving to the
active group when claimed.

### Acceptance Criteria

Copied verbatim from the source story:

- Given queued items exist, when I view the list, then they appear below active items, differentiated by
  their own label/icon/colour.
- Given a queued item is claimed and becomes active, when that happens, then it moves from the queued
  group into the active group.
- Given a row's title is longer than one line, when it doesn't fit, then it wraps to a second line rather
  than being truncated with an ellipsis.
- Given a queued item, when it appears in the list, then its next step name is shown.

### Dependencies

- WI-010.

### Constraints

- **Must read `StatusUseCase.lanes`' separated `queue` key, not `QueueUseCase`'s merged
  `queue`+`blocked`.** Using the wrong use case would put blocked/dependency items in the bottom group
  instead of the top needs-attention group, contradicting WI-011/WI-017.
- Uses the shared design-system tokens for icon/colour/grid.

### Verification

- Pilot test: a queued fixture item renders at the bottom, correct icon/colour, next-step name shown.
- Pilot test: a queued item transitioning to `in_progress` across two poll ticks moves from the queued
  group into the active group.
- Regression test asserting the queued group's source is `StatusUseCase.lanes["queue"]`, not
  `QueueUseCase`'s merged output - guards against the exact mistake the Context field above warns about.

Queued items render correctly at the bottom, move to active on claim, sourced from the correct
