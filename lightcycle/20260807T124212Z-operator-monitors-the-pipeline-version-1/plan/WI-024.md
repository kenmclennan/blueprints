## WI-024: Footer: contextual shortcut bar

**Brief:** The footer's shortcut line always lists exactly the keys valid right now - not a static
per-screen list, since the same screen's shortcut set contracts and expands with data state (e.g. the
Priority List's empty state drops from six shortcuts to just `tab`/`q`). This item establishes the
contextual-footer mechanism using the Priority List's own normal and empty states (both already built by
WI-011-013 and WI-016), which later screens reuse rather than re-deriving.

### Acceptance Criteria

Copied verbatim from the source story:

- Given any screen, when I look at the footer, then it lists only the shortcuts relevant to that screen
  (e.g. 'a artifacts / l log' shows only in the tree).
- Given the screen changes, when that happens, then the footer's shortcut list updates to match.

### Dependencies

- WI-016 (the Priority List's empty state, needed to demonstrate the contraction this item builds
  against).

### Constraints

- The mechanism established here (shortcut visibility as a function of screen AND data state, not screen
  alone) is reused by name in every later screen's own work item (hub, artifacts, log, backlog) - each
  later item's own footer content is part of its own scope, not re-derived here.
- An open overlay (e.g. Backlog's filter picker, built in WI-053) does not replace the persistent
  footer's shortcut line - the overlay shows its own hints separately. This item establishes that
  boundary even though the picker itself is built later.
- **The wireframe's normal-state six-shortcut list is the design's final, fully-built state - not a
  literal snapshot of what's true the moment this item lands.** `enter/→ open` is only a genuinely valid
  action once WI-026 (opening an item into its detail view) exists; per this item's own AC ("lists only
  the shortcuts relevant to that screen"), the mechanism built here must derive the shortcut list from
  which actions are actually wired up, not hardcode the wireframe's full list ahead of the functionality
  existing. Concretely: at Milestone 1 (before WI-026 lands), the Priority List's normal state correctly
  shows five shortcuts, not six; `enter/→ open` joins the set automatically once WI-026 lands, with no
  further change needed to this item's own code - this is the mechanism working as designed, not a defect
  to route around.

### Verification

- Pilot test: Priority List normal state, as buildable at this item's own point in the sequence (before
  WI-026 exists), shows the shortcuts for actions actually wired up (`↑↓` move, `tab` backlog,
  `ctrl-u/ctrl-d` scroll, `q` quit) and does not show `enter/→ open`.
- Pilot test: Priority List empty state (WI-016) shows exactly `tab`/`q`, nothing else.
- Pilot test: transitioning between normal and empty states (simulated poll) updates the shortcut line
  without requiring a screen change.
- Follow-up regression (executed once WI-026 lands, not part of this item's own build): the normal
  state's shortcut list grows to include `enter/→ open` with no code change required in this item.

### Deliverable

The footer's shortcut line is driven by a screen+data-state function, verified correct on the Priority
List's two existing states at this item's own point in the build sequence, ready for later screens (and
later actions on the same screen) to plug into without further changes here.
