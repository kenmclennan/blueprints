# WI-009 - Hierarchy tab visual and escalation fidelity

## What

Filed by `audit-design` against the built Hierarchy tab and hub escalation panel, not by a story - four gaps found by rendering the real composited screen and reading `hub.py` against `wireframe-hub.html`, none of them the already-filed LC-273/275/277/282/284/289.

## Reproduced

1. **The hierarchy tree's row area paints a background colour that is not a design token.** `NodeHubScreen.CSS` never sets a background for `HierarchyPagingTable`; Textual's own default fills it in. Extracting real `bgcolor` (not just foreground) from the composited frame on `hub#hierarchy` shows 86 cells at `#272727` - a colour absent from [Design System Tokens](../design-system/design-system-tokens.md)'s colour table entirely - against 122 cells correctly at `--bg` (`#0c0c0f`) and 10 at `--selected-bg` on the cursor row. [wireframe-hub.html](../wireframes/wireframe-hub.html)'s `.term`/`.body` rules never declare a distinct panel background for the tree area - only the current row gets `--selected-bg`. In the running app the whole hierarchy area reads as a visibly different grey box floating inside the hub frame, which the design never specifies and the token set has no name for.
2. **The pinned-ancestor row drops the state icon the wireframe gives it.** [wireframe-hub.html](../wireframes/wireframe-hub.html)'s `.pinned-ancestor` markup includes an `.icon` span alongside the id and title, matching every other row. `NodeHubScreen.update_pinned_ancestor()` (`hub.py:872-895`) builds the pinned banner as `"%s  %s" % (ancestor.node.id, ancestor.node.title)` with no glyph. Reproduced by scrolling `hub#hierarchy-scrolled` deep enough to pin an ancestor: the banner renders as `LC-290.1  Deliver the operator-monitors-the-pipeline Blueprint` with no leading state icon - the one row whose entire purpose is keeping ancestor context visible (["Keep ancestry visible while I scroll"](../user-stories/eaa87e0b-0a4f-4c35-b3ff-d372ec1a286f.md)) silently drops that ancestor's own state.
3. **The escalation panel is missing its "needs you" tag and uses the wrong colour treatment for the reason text.** [wireframe-hub.html](../wireframes/wireframe-hub.html)'s `.escalated` block (both the blocked-dependency and needs-attention-human states) is two lines: a bold amber tag (`⚠ needs you`) plus a `--text`-coloured reason line whose blocking id/PR is coloured `--cyan` as a link. `HubHeader.update()` (`hub.py:290-298`) instead does `panel.update(Text(header.escalation_text, style=COLOURS["amber"]))` - a single line, entirely amber, no tag text anywhere (`hub.py`'s only `⚠` is an unrelated toast-failure prefix), and `#hub-escalation { height: 1; }` structurally rules out the wireframe's two-line layout regardless. Verified by colour-extracting `hub#blocked-dependency`: one uniform `#e0a95f` span, `Blocked · depends on LC-143.1.4`, no tag, no link colouring on the id. This is the visual treatment behind ["See why an item is escalated"](../user-stories/4bee4625-16c6-4f37-a7af-01893eba78ea.md) - the reason text is present, but not the design's way of flagging why it needs attention.
4. **The `l` hierarchy jump key silently no-ops on an item or theme row even when its current step is live, inconsistent with `Enter` on the same row.** `HierarchyPagingTable.action_jump_log()` (`hub.py:378-386`) unconditionally returns unless `node.type == "step"`. But this same file's `landing_node`/`log_target_node` helpers already resolve an active item to its current step everywhere else in the hub - including `Enter`, which correctly opens an active item's Log tab. Reproduced: with the cursor on `LC-143.3` (an active item whose current step is `in_progress`) in the hierarchy tab, pressing `l` leaves the screen completely unchanged; pressing `Enter` on the identical row correctly lands on the Log tab. [Keyboard Navigation Scheme](../design-system/keyboard-navigation-scheme.md) states `l` is "no-op on a human step or a step that hasn't run" - it does not say item/theme rows with a live current step should be excluded, and [`Jump straight to a node's artifacts or log from the hierarchy`](../user-stories/8f6e008e-f9d8-4c6d-a061-02da7002bd42.md) doesn't restrict itself to step-type rows either.

## Defined by

- [wireframe-hub.html](../wireframes/wireframe-hub.html) - the `.pinned-ancestor` and `.escalated` markup for points 2 and 3.
- [Design System Tokens](../design-system/design-system-tokens.md) - the colour token table point 1 is checked against.
- [Keyboard Navigation Scheme](../design-system/keyboard-navigation-scheme.md) - the `a`/`l` jump-key contract point 4 is checked against.
- [Keep ancestry visible while I scroll](../user-stories/eaa87e0b-0a4f-4c35-b3ff-d372ec1a286f.md), [See why an item is escalated](../user-stories/4bee4625-16c6-4f37-a7af-01893eba78ea.md), [Jump straight to a node's artifacts or log from the hierarchy](../user-stories/8f6e008e-f9d8-4c6d-a061-02da7002bd42.md).

## In scope

- Giving the hierarchy tree area a background that matches a real design token (most likely `--bg`, matching the rest of the frame) or, if a distinct panel treatment is actually wanted, adding that token to the design system first.
- Adding the state icon to the pinned-ancestor row.
- Making the escalation panel two lines with the tag/reason/link colour treatment the wireframe shows, which requires lifting `#hub-escalation`'s fixed `height: 1`.
- Deciding and implementing `l`'s behaviour on an item/theme row with a live current step, consistent with what `Enter` already does on the same row.

## Out of scope

- The row-grid column overflow issues filed separately as WI-008.
- Anything already filed as LC-273, LC-275, LC-277, LC-282, LC-284, or LC-289.

## Done when

The hierarchy tree area's background matches a named design token, the pinned-ancestor row shows its state icon, the escalation panel renders as the wireframe's two-line tagged treatment, and `l` behaves consistently with `Enter` on item/theme rows with a live current step - each verified on the actual composited frame.

## Open questions

- `[builder]` Whether `l` on an item/theme row with no live current step (queued, or a human gate) should stay a no-op the same way it already is for a step in that state - the story language suggests yes, but it's not stated as explicitly as the step case is.
