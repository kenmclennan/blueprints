## WI-009: Dependency-rule + `adapters/` doc reword; Textual added as a runtime dependency

**Brief:** Two of the engine's own standing rules, read literally today, forbid this design: "zero
runtime dependencies" and "`adapters/`... the only callers of sqlite3/git/subprocess" (a driven-adapter
framing that doesn't obviously cover a driving adapter like the TUI). These are Changes 2 and 3 in the
Architecture artifact - explicitly this design's own delivery, not a follow-up. This item rewords both
rules to state their real scope, and lands Textual as a normal (not extras-gated) dependency of the
`lightcycle` distribution, since every other Milestone 1+ item needs it importable.

### Acceptance Criteria

Restated in Given/When/Then form from the architecture doc's own two named changes:

- Given the current zero-runtime-dependencies rule in `CLAUDE.md`, when it's reworded, then it explicitly
  states the stdlib-only constraint applies to code that runs unattended (the pool loop and everything a
  worker touches via `lc claim`/`lc done`), not to a driving adapter a human launches interactively - the
  rule's existence is unchanged, only its stated scope narrows to match reality.
- Given the current `adapters/` description in `CLAUDE.md`, when it's reworded, then it explicitly covers
  driving adapters (like the TUI) alongside the existing driven-adapter examples (`SqliteStore`, git,
  etc.), matching how `cli.py` already calls use cases rather than IO directly, without cli.py itself
  needing to be reclassified.
- Given `pyproject.toml`, when Textual is added, then it's added as a normal dependency (not under
  `[project.optional-dependencies]` / an extras group) - an opt-in extras flag would only protect a
  hypothetical non-TUI user who doesn't exist for this deployment.
- Given the unattended path (pool loop, worker-touched code), when it's audited after this change, then
  it still imports no third-party package - this item narrows the rule's stated scope, it does not
  relax what the unattended path itself may import.

### Constraints

- Confirmed against live code (2026-08-11), exact current wording to replace:
  - Zero-runtime-deps rule (under "## Style"): "**The engine ships zero runtime dependencies.** Code
    under `lightcycle/` imports the stdlib only - no third-party `import` ever reaches the shipped
    engine (it keeps the fork portable, the trust surface small, and 'clone and run' true). **Dev/test
    tooling is separate and pragmatic**: it lives in `pyproject.toml`'s dev group, managed by `uv`, and
    never imported by `lightcycle/` (currently `pytest` + `pytest-bdd`). The hard line is _runtime_, not
    _tooling_."
  - `adapters/` description (under "## Architecture: hexagonal (DDD)"): "`lightcycle/adapters/` - all
    IO: the sqlite store (`SqliteStore`), git, the worker spawner, the workers registry, the filesystem.
    The only callers of `sqlite3` / `git` / `subprocess`."
- Confirmed `pyproject.toml` currently has `requires-python = ">=3.11"`, `dependencies = []`, no
  `[project.optional-dependencies]` section at all - so there is no existing extras-gating pattern to
  follow or avoid; this item establishes plain runtime dependency addition as the mechanism.
- Confirmed `lightcycle/adapters/` currently contains no `tui/` subdirectory - this item does not create
  it (that's WI-010's job); it only clears the documented rule that would otherwise block it.
- The real git adapter file is named `gitio.py`, not `git.py` - the architecture doc's own "alongside
  `sqlite_store.py`, `git.py`" phrasing should be corrected to `gitio.py` when the doc is touched, since
  this item is already editing adjacent text.
