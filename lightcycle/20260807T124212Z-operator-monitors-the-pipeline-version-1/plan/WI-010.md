## WI-010: TUI app scaffold: launch, connect, render, footer frame

**Brief:** Stand up the Textual app itself - the entry point, the module at
`lightcycle/adapters/tui/`, in-process connection to the existing read-only use cases, and the first
render of a priority list (ungrouped is acceptable at this point - grouping is WI-011/012/013) plus a
visible footer frame. This is the first genuinely observable slice of the whole design.

### Acceptance Criteria

Copied verbatim from the source story:

- Given the lightcycle store is reachable, when I launch the dashboard, then it renders the priority list
  within about a second.
- Given the dashboard has just launched, when it renders, then the footer status bar is visible
  immediately alongside the list, not as a separate loading step.

### Dependencies

- WI-009 (Textual must be a real dependency and the driving-adapter rule must be cleared before this
  module can exist).

### Constraints

- Terminal-Native, No Server principle: "Read state directly from the same store/log files `lc` already
  writes... in-process or via the engine's read-only use cases - never through a new HTTP/websocket
  server."
- Module placement: `lightcycle/adapters/tui/`, a driving adapter per the architecture doc.
- The 10-second poll loop (`set_interval`) is established here as the mechanism every later Milestone 1+
  item's "live-updating" behavior builds on - do not re-derive it per screen.

### Verification

- Textual `Pilot`-driven test: launching the app against a fixture store renders a priority list and a
  footer frame within the test harness's time budget.
- Manual/integration check: launch against the real dev store, confirm sub-second first render.
- **Unit test asserting the poll interval constant equals 10 seconds** (`quality-attributes.md`'s
  "Staleness bound: at most ~10 seconds plus render time"). Added during this plan's own Pass 7
  adversarial review, which found the ~10s staleness bound asserted throughout this design but never
  concretely checked by any work item - every other item's own tests are phrased relatively ("updates
  without a full list refresh," "one poll interval of lag"), which would pass unchanged even if the
  interval were quietly set to 60s. This is the one place to pin the literal constant, since every later
  item's poll-driven behavior reuses this same `set_interval` call rather than declaring its own.

### Open Questions

- `[builder]` Exact CLI entry point name/invocation (e.g. `lc tui`) - not specified anywhere in this
  design.
- `[designer]` Dashboard behavior when `store.db` is unreadable at launch (missing, corrupt, or
  otherwise unopenable) is not specified anywhere in this design. Quality Attributes' own "Resilience"
  section states this directly rather than answering it: "Everything else is local, so the main failure
  mode is a missing or corrupt store, not a network failure. No story or architecture text currently
  specifies dashboard behaviour if `store.db` is unreadable at launch - noted as an open question below
  rather than answered speculatively." No principle or other artifact resolves it either.

### Deliverable

`lightcycle/adapters/tui/` exists with a launchable Textual app that connects in-process, renders a
priority list of current steps (ungrouped at this stage) and a footer frame, within about a second,
tested via Pilot.
