# WI-010 - Footer status line on the Artifact Viewer screens

## What

Filed by `audit-design`, not by a story. The footer's status line - pool, Claude availability, version, upgrade - renders correctly on every screen WI-003 was scoped against, but is entirely blank on the two Artifact Viewer screens that actually push a live status update mechanism (the text and list viewers): `StatusBar.report(...)` is simply never called there.

## Reproduced

Verified against `origin/main` at `6cee3b9` via `tests/support/tui_harness.py` reading the actual composited frame. `python -m tests.support.screen_render artifact-viewer#text` and `artifact-viewer#list` both show:
```
──────────────────────────────────────────────────────────────────────────────────────────────────│
                                                                                                    │
↑↓ scroll  ctrl-u/ctrl-d page  esc/← back to artifacts  tab backlog  q quit                        │
```
The shortcut-keys line renders (`ShortcutBar.set_shortcuts()` runs unconditionally in `DashboardFooter.on_mount`); the status line above it stays blank on both screens - no pool indicator, no Claude-availability indicator, no version, no upgrade indicator.

Root cause: `grep -rn "\.report(" lightcycle/adapters/tui/` finds exactly two call sites - `app.py:521` (the base screen's own footer, wired to the app's 10s poll) and `hub.py:731` (`NodeHubScreen._refresh_footer`, wired to the hub's own poll/init). `TextArtifactViewerScreen.on_mount` (`hub.py:536-541`) and `ListArtifactViewerScreen.on_mount` (`hub.py:550-563`) each compose a `DashboardFooter` (which contains a `StatusBar`) but never call `.report()` on it, and set up no interval that would. The URL/filepath "toast" artifact kinds are unaffected, since they render as a toast inside the existing hub screen rather than pushing a new one, so the hub's own footer wiring still applies to them.

## Defined by

- [Design System Tokens](../design-system/design-system-tokens.md) - "Footer": "Two-line footer, present on every screen: a status line... above a contextual shortcut-keys line."
- [wireframe-artifact-viewer.html](../wireframes/wireframe-artifact-viewer.html) - its own footer explicitly renders `● pool running` and the version, in both the text-artifact and list-artifact states.
- [See which engine version is running](../user-stories/131f76a9-7b9b-4d70-889c-5c0e9c9a0d3d.md), [See whether Claude is available to process work](../user-stories/02c20dfb-88af-4b91-887b-6c9f1fa660aa.md), [See whether the pool is running](../user-stories/34603aed-522d-4835-9836-00b99abf31ea.md) - each states or implies the segment is visible on every screen, not conditionally.

## In scope

- Wiring `StatusBar.report(...)` (or an equivalent live update) into `TextArtifactViewerScreen` and `ListArtifactViewerScreen`, matching how the base screen and the hub already do it.

## Out of scope

- The URL/filepath toast states - already correctly footed via the hub screen underneath them.
- Anything already filed as WI-003 or WI-007's original scope, or as LC-273/275/277/282/284/289.

## Done when

The footer's status line - pool, Claude availability, version, upgrade-when-available - renders and stays live on the text and list Artifact Viewer screens, verified on the actual composited frame.
