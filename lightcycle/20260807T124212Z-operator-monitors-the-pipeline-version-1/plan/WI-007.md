## WI-007: Durable done-step log resolution

**Brief:** Both existing log-resolution paths (`TraceUseCase._log_for_step`, `ResolveLogUseCase`)
find a step's log purely by scanning the live workers registry (`workers.json`) for a matching entry -
and that registry is trimmed to a bounded depth by the pool's sweep (`prune_workers`). A done step's
worker entry surviving long enough to still be found there is not guaranteed, even though the underlying
log file itself is never deleted from `logs/`. WI-049 ("See a done step's historical log") depends on
resolving a done step to its log reliably, independent of registry pruning.

### Acceptance Criteria

Restated in Given/When/Then form from the story that depends on this gap being closed:

- Given a step is done and its worker registry entry has NOT yet been pruned, when its log is resolved,
  then the existing registry-scan path continues to work exactly as it does today (no regression).
- Given a step is done and its worker registry entry HAS been pruned by `prune_workers`, when its log is
  resolved, then the underlying log file in `logs/` is still found and returned - the resolution no
  longer depends solely on a live registry entry surviving.
- Given a step has never run (queued, or a human step), when its log is resolved, then no log is found
  (nothing to distinguish from "pruned" here - both correctly report absence).

### Dependencies

None.

### Constraints

- Confirmed against live code (2026-08-11): `_log_for_step` (`application/work/trace.py`) scans
  `self._workers.workers_state()` most-recent-first by matching `step` - confirmed registry-only.
  `prune_workers` (`adapters/workers.py`, invoked from `application/pool/sweep.py`'s `SweepUseCase`)
  keeps only the newest dead entries up to `keep_dead` (the config's `worker_history()`) - confirmed
  bounded, confirming a done step's entry is not guaranteed to survive.
- The log FILE itself is never deleted (`logs/` is append-only per-run) - this item is purely about
  resolving the step-id → log-path mapping durably, not about log retention.

### Verification

- Unit test: log resolution succeeds via the existing registry-scan path when the entry is present
  (regression).
- Unit test: log resolution succeeds when the registry entry has been pruned but the log file still
  exists on disk.
- Unit test: a step that never ran resolves to no log, distinctly handled from a pruned-but-real log.

### Open Questions

- `[builder]` Exact mechanism - a durable log-path column/record written at spawn time (surviving
  registry pruning independently), a deterministic filename convention the resolver can reconstruct from
  the step id without a registry lookup at all, or another approach. Not specified by the design.

### Deliverable

A log-resolution path that reliably finds a done step's historical log file even after its worker
registry entry has been pruned, unit-tested against both the present-entry and pruned-entry cases.
