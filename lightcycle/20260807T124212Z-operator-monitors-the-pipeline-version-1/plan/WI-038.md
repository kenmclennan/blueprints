## WI-038: See why an item is escalated + jump to the blocker and back

**Brief:** In the hub header's escalation block, name the specific reason a needs-attention item is
escalated: a named blocking dependency (with a jump-to-it link), or what a human step is asking of the
operator. No escalation reason renders for an active or queued item.

### Acceptance Criteria

Copied verbatim from the source story:

- Given an item is blocked on a dependency, when I open its detail view, then it names the specific
  blocking dependency.
- Given an item's current step is escalated (e.g. rejected, needing rework), when I open its detail view,
  then it names what's being asked of me.
- Given an item is active or queued, not needs-attention, when I open its detail view, then no escalation
  reason is shown.
- Given an item is blocked on another item's completion, when I select the named blocking item with Enter
  or →, then I'm taken straight to that item's own detail view.
- Given I jumped to a blocking item's hub via that link, when I press Esc or ←, then I return to the
  original, blocked item's hub - not the priority list - at the tab I was on.

### Dependencies

- WI-027 (hub header, where the escalation block lives), WI-006 (blocking-dependency-id resolution).

### Constraints

- **Confirmed against live code (2026-08-11): the human-step reason is written by `BlockStepUseCase`
  (`application/flow/block_step.py`, not `application/work/complete_step.py`) as exactly
  `route_to_human(step, "BLOCKED: %s" % needs)`** - a free-text note, already live, no engine gap on that
  half. Only the dependency-naming half (AC-1/AC-4) depends on WI-006's resolution.
- Jump-and-return (AC-5) must land back on the *originating blocked item's hub*, at the tab it was on -
  not the priority list, and not the blocking item's own prior screen. This is a deeper back-stack entry
  than WI-026/WI-036's single-level Esc contract - verify it explicitly, since a naive single-level
  Esc/back implementation could instead return to wherever the blocking item's hub was itself opened from.

### Verification

- Pilot test: a dependency-blocked item's hub names the specific blocking id and it's selectable.
- Pilot test: a human-step-escalated item's hub names the free-text reason from `needs`.
- Pilot test: an active or queued item's hub shows no escalation block at all.
- Pilot test: selecting the blocking-item link opens that item's own hub; pressing Esc/← from there
  returns to the *original* blocked item's hub, at the tab it was on - not the priority list.

### Deliverable

Escalation reasons render correctly for both dependency and human-step cases, with a working jump-to-
blocker-and-back navigation.
