## WI-055: Read-only planned-step projection from the pinned workflow graph

**Brief:** Added via this plan's own Pass 7 adversarial review, not originally scoped - see "Provenance"
below. Every Hierarchy tab wireframe state shows an item's *entire* step sequence, including steps well
past the current one (e.g. LC-143.3 at step 4 of 8, with steps 5-8 rendered as ordinary rows with real
ids like `LC-143.3.5`). The live engine never files a step before it's reached - `create_step`/
`_insert_step_nocommit` are called exactly once per transition (`step_filing.py`'s `file_step` for an
entry step, `next_step.py`'s `next_step_spec` for every subsequent one), never in a batch, never ahead of
time. Steps 5-8 in that wireframe cannot be real `nodes` rows at the point the operator is viewing them.
This item adds a read-only projection, walking the item's pinned workflow's resolved graph (`Flow.
routes`, already built by `Flow.from_graph` from the workflow bundle - not a new parsing mechanism) along
the normal/expected outcome path from the current step, to produce the remaining "planned" steps the
Hierarchy tab needs to render the wireframe's full sequence.

### Acceptance Criteria

Restated in Given/When/Then form - this item has no authoring story (see Provenance), so criteria are
derived directly from what the Hierarchy tab wireframe states requires and what the verified engine
constrains:

- Given an item's current step and its pinned workflow (`origin/name@sha`), when the projection runs,
  then it returns the sequence of step names (and their roles) the item's workflow graph names as coming
  after the current step along its normal/expected outcome path - not real `Node` rows, since none exist
  yet.
- Given a projected step's position under its parent item (1st, 2nd, 3rd... after the ones already
  filed), when an id is needed for display, then it's computed positionally (matching the engine's
  existing id-nesting convention - `LC-143.3.5` is simply the 5th child of `LC-143.3`, computable without
  a real row existing), not read from any store row.
- Given the workflow graph reaches a genuine branch point (more than one possible next step depending on
  outcome - e.g. `watch-ci`'s `ci-failed` retry loop vs. its success path), when the projection walks
  past it, then it follows only the normal/expected-completion edge, never a retry, escalation, or
  rework edge - see Open Questions for how "normal/expected" is determined where the workflow format
  doesn't mark one explicitly.
- Given the workflow graph terminates (an edge with no `next-step`, per the engine's own "a
  next-step-less edge declares the outcome terminal" convention), when the projection reaches it, then it
  stops there - the projected sequence is finite and ends at the workflow's real terminal step.
- Given a step has already been filed as a real `Node` row, when the projection is asked for that item's
  steps, then it does not project a step that already exists - real, filed steps and projected, planned
  steps never overlap or duplicate.

### Dependencies

None (Milestone 0).

### Constraints

- **Read-only, in-process, via the already-loaded `Flow` object** - no new workflow-bundle parsing, no
  store schema change. This is purely a walk over data the engine already resolves at load time.
- Must never create, or imply the future creation of, a real `Node` row - "Observation Only" applies here
  exactly as everywhere else: a projected step is a display fact about the workflow's shape, not a
  reservation or claim on anything.
- The Hierarchy tab (WI-030) renders real and projected steps together but must be able to tell them
  apart - a projected step has no real state, role-as-performed, or artifacts, only a name and a
  positionally-computed id.

### Verification

- Unit test: a fixture item mid-workflow (some steps filed, more remaining) projects the correct
  remaining sequence with correctly computed positional ids.
- Unit test: a fixture workflow with a branch (a capped retry edge alongside a success edge) projects only
  along the success path, stopping neither early nor incorrectly extending into the retry loop.
- Unit test: a fixture item at its workflow's last step projects an empty sequence (nothing planned -
  correctly recognizes the terminal edge).
- Unit test: projected steps never duplicate or overlap with real filed steps for the same item.

### Open Questions

- `[designer]` How "the normal/expected-completion edge" is determined at a branch point where the
  workflow format doesn't mark one explicitly (e.g. a step with more than one non-retry, non-escalation
  outcome edge) - this item's own scope (and the wireframe's own single example) only demonstrates the
  case where exactly one non-exceptional edge exists at each branch encountered (`watch-ci`'s success
  path, distinct from its capped `ci-failed` retry). Whether a workflow author must mark a "primary" edge
  explicitly, or the projection infers it by excluding known retry/escalation hook types, is unresolved.
- `[designer]` No visual treatment for a "planned, not yet filed" row exists in `design-system-tokens.
  md`'s state-to-icon/colour table (needs-attention/active/queued/selection-cursor only) - the wireframe
  reuses the plain queued `○` icon for these rows, visually identical to a real queued step, even though
  the two behave completely differently when selected (see WI-036/WI-037's own open questions on this).
  Whether that's the intended final treatment or an under-specified gap in the wireframe is not settled
  by anything else in this design.

### Deliverable

A read-only projection, reusing the already-loaded `Flow` graph, that returns an item's remaining planned
steps (name, role, computed id) along its workflow's normal-completion path, stopping correctly at
branches and termination, with unit tests covering the branch and termination cases explicitly.

## Provenance

This item did not exist in the original decomposition - it surfaced during this plan's own required Pass
7 adversarial review (`references/verification.md`), which found that WI-030/031/033/034/035/036/037 (the
whole Hierarchy tab) were built assuming every row shown in the wireframe corresponds to a real `Node`
row, which is false for any step past the current one. See `plan/verification.md` for the full review.
