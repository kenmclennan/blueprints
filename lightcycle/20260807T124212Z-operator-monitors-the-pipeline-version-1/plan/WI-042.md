## WI-042: Follow a URL artifact

**Brief:** Open a `url`-kind artifact via `webbrowser.open()`. Since the browser takes over, there's no
separate viewer screen to sit in - show a brief confirmation toast and return straight to the artifact
list. Show a clear message (not a silent failure) if opening fails.

### Acceptance Criteria

Copied verbatim from the source story:

- Given an artifact declares kind `url`, when I select it with Enter or →, then it opens in the system's
  default browser.
- Given the URL fails to open (e.g. no browser available), when that happens, then I see a clear message
  rather than a silent failure.
- Given the URL opens successfully, when that happens, then the TUI shows a brief confirmation toast and
  returns to the artifact list - there's no separate viewer screen to sit in, since the browser has taken
  over.

### Constraints

- No separate viewer screen exists for this kind by design - the toast-and-return is the entire UI
  surface, not a placeholder for a fuller screen.
- Per hexagonal architecture's port/adapter split (`architecture/tui-architecture.md`, "Module
  placement"), `webbrowser.open()` is IO the same way `SqliteStore`/git are - it belongs behind a small
  driven adapter the TUI (a driving adapter) calls through a port, not an inline call scattered in screen
  widget code. This keeps the browser-open call unit-testable via a fake and consistent with `adapters/`'s
  own "only callers of subprocess"-style boundary (broadened by WI-009 to include driving adapters, which
  does not relax this rule for driven IO like this one).

### Verification

- Pilot test: a `url`-kind artifact triggers `webbrowser.open()` with the correct URL and shows the
  confirmation toast, returning to the artifact list automatically.
- Pilot test: a mocked browser-open failure shows a clear failure message, not silence.

### Deliverable

URL artifacts open correctly in the default browser with a working toast-and-return flow and a clear
failure message on error.
