## WI-036: Open a node from the hierarchy + return without losing position

**Brief:** Any node (theme, item, step) selected in the Hierarchy tab opens into its own tabbed hub -
uniformly, regardless of node type - landing on the tab matching its own state (reusing WI-028's logic
recursively). Closing returns to the Hierarchy tab at the same node and scroll position. Bundled for the
same reason as WI-026: a drill-down within the hierarchy needs its own way back to be releasable.

### Acceptance Criteria

Copied verbatim from "Open a node from the hierarchy":

- Given any node (theme, item, or step) is selected in the hierarchy, when I confirm the selection with
  Enter or →, then it opens into its own tabbed hub, landing on the tab that matches its state.
- Given the selected node is a step rather than a theme or item, when its hub opens, then the header shows
  its role and state in place of the theme/workflow/description fields, which only apply to themes and
  items.

Copied verbatim from "Return to the hierarchy tab without losing position":

- Given I opened a node from the Hierarchy tab, when I close it with Esc or ←, then the Hierarchy tab
  reappears with that node still selected and scrolled to the same position.

Added to close a gap found during this plan's own Pass 7 adversarial review (not part of either source
story - see Provenance in WI-055): a Hierarchy row can be a WI-055-projected planned step, which has no
real `Node` to open at all.

- Given the selected row is a planned (not-yet-filed) step from WI-055's projection, when I confirm the
  selection with Enter or →, then nothing opens - there is no real node behind it yet - and the selection
  stays exactly where it was, consistent with this design's "no artifact is ever unopenable, no
  action ever fails silently-broken" instinct rather than attempting to open a node that doesn't exist.

### Dependencies

- WI-030, WI-004 (role on the read path), WI-027 (the STEP/ROLE header fields this item's own AC-2
  requires for a step opened from the hierarchy - this item explicitly reuses WI-027's rendering, so the
  dependency is real, not merely referenced in prose), WI-055 (planned-step rows, which this item must
  handle as a distinct, non-openable case).

### Constraints

- Opening any node from the hierarchy recursively reuses WI-028's tab-landing logic and WI-026/WI-027's
  header rendering (with the step-vs-item/theme field substitution this item's own AC-2 specifies) - not
  a separate hub implementation.
- Recursion is bounded: opening a node from the hierarchy can itself show that node's own Hierarchy tab,
  from which another node can be opened, and so on up to the tree's own three-level depth bound (see
  WI-035) - no unbounded nesting concern.
- A planned (WI-055-projected) row is never treated as if it were a real node - confirm its "no real
  `Node` id" before attempting to open, not after a failed lookup.

### Verification

- Pilot test: selecting a theme, an item, and a step in turn from the hierarchy each open a correctly
  populated hub (step shows STEP/ROLE header fields; theme/item show identity/description fields).
- Pilot test: opening a node from the hierarchy then closing with Esc returns to the Hierarchy tab at the
  same node, same scroll position.
- Pilot test: selecting a planned (not-yet-filed) row and pressing Enter does nothing observable - no
  navigation, no error, selection unchanged.

### Deliverable

Every node type opens correctly from the hierarchy into its own hub; closing returns precisely to the
hierarchy's prior state.
