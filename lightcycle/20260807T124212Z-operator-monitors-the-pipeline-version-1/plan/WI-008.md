## WI-008: Backlog per-project counts (all projects at once)

**Brief:** `BacklogUseCase.execute` only ever returns rows (and an optional theme-grouped breakdown) for
whichever single `project` filter it's given - there's no call that returns every registered project's
own count independent of which filter is active. The Backlog filter picker (WI-053) needs exactly that,
up front, before any filter is chosen; the empty-state distinction between "empty overall" and "empty
under this filter" (WI-054) needs the same underlying capability.

### Acceptance Criteria

Restated in Given/When/Then form from the two stories that independently depend on this gap:

- Given N projects are registered plus any unscoped backlog items, when the new read path is called, then
  it returns every registered project's own backlog item count, plus the unscoped/"All" count, in one
  call - not one call per project.
- Given the current single-filter `BacklogUseCase.execute(project=X)` is called separately, when compared
  to the new all-projects read, then both remain consistent with each other and neither call needed to
  invoke the other project-by-project to answer its own question.
- Given zero backlog items exist for a specific registered project, when the new read path is called,
  then that project still appears with a count of zero (not omitted) - so the picker can show it as a
  real, selectable, empty option.

### Constraints

### Verification

  unscoped bucket, against a fixture with a known distribution.
- Unit test: a registered project with zero backlog items still appears with count zero.
- Regression: existing `BacklogUseCase.execute(project=X)` single-filter behavior unchanged.
