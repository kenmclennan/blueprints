# WI-008 - Row-grid columns hold under realistic id, role, and type lengths

## What

Filed by `audit-design`, not by a story - this is a fidelity gap the design's own row grids create against realistic data, found by running the built screens rather than reading their code. Every fixed-width `id` column in the row grids (Priority List, Backlog, Hierarchy), the Hierarchy tab's `role` column, and the Artifacts tab's `type` column, silently break once real content exceeds the token width: the Priority List wraps the id onto a second line, corrupting the one-row-per-item grid every other story assumes; the Backlog, Hierarchy, and Artifacts tabs instead hard-truncate with no ellipsis, silently dropping characters - in the worst case producing a truncated id that is itself a plausible, different, real-looking id, not an obviously-cut fragment. None of this is theoretical - it reproduces with realistic ids, role names, and artifact types, not contrived extremes.

## Why this is a design gap, not just a build defect

[Ontology](../glossary/ontology.md)'s own "Identity" section states a project's shortcode is "Explicit at registration (`--shortcode`) or defaulted from identity's name segment, uppercased" - and the engine's default (`identity.split("/")[-1].upper()`, `lightcycle/application/setup/project_scan.py`) is genuinely unbounded: a project registered without an explicit short code gets its whole repo name as its shortcode (e.g. `LIGHTCYCLE`, ten characters, not the two-character `LC` every wireframe and demo fixture happens to use). Every id in that project then nests off an already-long root (`LIGHTCYCLE-3.1.1` is sixteen characters), and [Design System Tokens](../design-system/design-system-tokens.md)' "Row grid conventions" table fixes the `id` column at `9ch` (Priority List, Backlog) or `13ch` (Hierarchy) with no stated overflow behaviour. The wireframes never render an id anywhere near these widths, so the gap was never visible in the design itself - only in the running app, against ids the design's own domain model already permits.

The Hierarchy tab's `role` column (`14ch`) has the same shape of problem from a different source: real step/role names in this very Blueprint's own workflow exceed it (`implement-features` is nineteen characters, `handle-feedback` is fifteen), so the same silent hard-truncation applies there too.

## Reproduced

All three, against `origin/main` at `6cee3b9` via `tests/support/tui_harness.py` reading the actual composited frame (`session.app.screen._compositor.render_strips()`), not a widget's own report of itself:

- **Priority List wraps the id, breaking the one-line-per-row grid.** With the repo's own demo data (`tests/support/screen_render.py`'s `_populated_store`), every three-segment step id wraps:
  ```
  │ ❯   ●     LC-143.3.  lightcycle  await merge                          code-await-merge           │
  │           6                                                                                      │
  ```
  `LC-143.3.6` is ten characters against a nine-character column. Reproduced independently with a plain `FakeStore`-generated id (`fake-56f47088`) too - not specific to this project's numbering.
- **Backlog silently truncates the id, with no ellipsis, and the result can itself be a different, plausible, real-looking id.** A todo item with a fourteen-character `FakeStore`-generated id (`fake-a72427b9`) renders as:
  ```
  │ ❯   fake-a724              Some backlog item                                                     │
  ```
  the trailing `27b9` is simply gone, not indicated as cut. Worse, with a realistic ten-character nested id, `LC-1234.10`, the Backlog renders:
  ```
  │ ❯   LC-1234.1              An item with an unusually long id                                     │
  ```
  `LC-1234.1` is not a truncation cue - it is a complete-looking, different id that could genuinely belong to another node (item 1 versus item 10 under theme `LC-1234`). An operator has no way to tell this row was cut at all.
- **Hierarchy tab truncates both id and role the same way.** With a project using the engine's own default (unshortened) shortcode, `LIGHTCYCLE-3.1` (an item) and `LIGHTCYCLE-3.1.1` (its step) both render as the identical `LIGHTCYCLE-3.`:
  ```
  │ ○         LIGHTCYCLE-3   Theme title                                                             │
  │ ○         LIGHTCYCLE-3.    Item title                                                            │
  │ ○         LIGHTCYCLE-3.      write the code                                       write-code     │
  ```
  and a step with `role="implement-features"` renders its role cell as `implement-feat` - hard-cut mid-word, no `…`.

The role truncation is not specific to this Blueprint's own workflow step names either: [Ontology](../glossary/ontology.md)'s own agent-step vocabulary names `handle-feedback` (15 chars), `resolve-conflict` (16) and `review-conflict` (15), all of which exceed the Hierarchy tab's `14ch` `role` column (`design_system.py:44`) and clip with no `…` - and the effective usable width is 13, not 14, since row cells are added at `height=1` (`hub.py:805`) with the widget's own cell padding eating the fourteenth column; even `feature-writer`, exactly 14 characters, clips to `feature-write`. No feature test exercises a role name at or over this width.

- **The Artifacts tab's `type` column truncates free-form artifact types the same way, with no ellipsis.** [`tui-architecture.md`'s Change 1](../architecture/tui-architecture.md) deliberately keeps artifact `type` free-form ("a workflow invents types freely"), so a long custom type is a case the design itself anticipates, not a hypothetical. `design_system.py:51` fixes this column at `10ch`. An artifact of type `code-review-findings` (a plausible workflow-defined type) renders as:
  ```
  │ code-revie  some value
  ```
  cut to `code-revie` with no `…` - the label shown isn't a real type at all.

- [wireframe-priority-list.html](../wireframes/wireframe-priority-list.html), [wireframe-backlog.html](../wireframes/wireframe-backlog.html), [wireframe-hub.html](../wireframes/wireframe-hub.html) - every row in every state they show is one line; none renders an id anywhere near the token widths, which is why this gap wasn't visible in the design itself.
- [TUI Architecture](../architecture/tui-architecture.md) - Change 1, which keeps artifact `type` free-form and so already anticipates a long custom type.
- [See the artifacts attached to a node](../user-stories/da91328b-2935-4b00-8444-63bd41cf0263.md) - "each is shown labeled by its type."
- WI-002, WI-004, WI-005, WI-007's own "done when" clauses, each of which already states rendering must be verified on the actual frame, not a widget's self-report - the standard this item is held to is the one those items already set, applied against data those items' own fixtures didn't exercise.

## In scope

- Implementing the column kinds, the atomic sizing rule, the breakpoint and the stacked layouts stated in [Design System Tokens](../design-system/design-system-tokens.md)' "Row grid conventions", across all four grids: Priority List, Backlog, Hierarchy tab, Artifacts tab.
- Confirming the id fix holds against the engine's own default (unshortened) shortcode, not just against short ones like this project's `LC`.

## Out of scope

- Changing the shortcode-derivation rule itself (`lightcycle/application/setup/project_scan.py`) - that is engine behaviour this design observes, not something this Blueprint owns.
- Changing what any column holds. The sizing rule classifies every column in all four grids, so `project`, `time`, `title`, `content` and artifacts' `value` are all governed by it - but none of them changes its contents, its order, or its meaning here.
- The project-filter picker's own count column, which drops to zero width for an unrelated reason (a missing width constraint on its label, not column-width overflow) - filed separately as WI-012.

## Done when

No atomic cell in the Priority List, Backlog, Hierarchy tab, or Artifacts tab ever wraps a row onto a second line or drops a character silently; the breakpoint stacks each grid as [Design System Tokens](../design-system/design-system-tokens.md) draws it; and the floor renders its message rather than a corrupted grid. Verified on the actual composited frame (not a widget's own `render_line`), against both this project's short (`LC`) ids and a project using the engine's own default, unshortened shortcode.

## Open questions

- `[builder]` Where the atomic width measurement lives - the widths are a property of the whole list, so they are computed once per refresh and handed to the grid, not derived per row.
