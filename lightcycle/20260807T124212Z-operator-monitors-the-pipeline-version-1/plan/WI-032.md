## WI-032: Hierarchy: content indicator per node

**Brief:** Show a small indicator on any hierarchy row whose node has at least one non-internal artifact,
filtering on WI-001's `internal` field. Data is already hydrated per-node by the existing `children()`
call - this item is purely a filter over an already-fetched field, not a new query.

### Acceptance Criteria

Copied verbatim from the source story:

- Given a node has at least one artifact whose internal flag is false, when it appears in the hierarchy,
  then it shows a content indicator.
- Given a node has only internal-flagged artifacts, or none at all, when it appears in the hierarchy,
  then no content indicator is shown.
- Given the content indicator is shown, when I open that node, then at least one artifact I can actually
  view is there.

### Source References

- **Artifact ID:** user-stories/9c53daa8-4b1a-425e-a3be-4f4a2ba53849.md
- **Section:** Context
- **Excerpt:** "Live-store analysis (2026-07-23) found artifact-presence alone isn't discriminating - 73%
  of items and 66% of steps have at least one. But most of that on steps is internal bookkeeping, not
  content... The wireframe's hierarchy state (wireframe-hub.html#hierarchy) doesn't actually render a
  content indicator - every row's icon column is identical regardless of content... so the indicator's
  glyph and where it sits in the row aren't specified... The underlying data is already there to filter,
  though: `children()` in `sqlite_store.py` hydrates each returned `Node` with its own `artifacts` list
  the same way `item_artifacts()` does for the Artifacts tab, so once change 1 (the `internal`/`kind`
  fields) lands, the indicator is a filter over a field the hierarchy's read model already carries per
  node, not a new query."

### Dependencies

- WI-030, WI-001 (the `internal` field this item filters on).

### Constraints

- Purely a display filter over already-hydrated data (`children()`'s existing per-node `artifacts` list)
  - no new query.
- AC-3 is a consistency guarantee, not new logic: since this filters the same `internal` flag WI-039
  (Artifacts tab) will filter on, showing the indicator and finding nothing viewable when opened would
  indicate a bug in one of the two filters disagreeing, not expected behavior.

### Verification

- Pilot test: a node with a mix of internal and non-internal artifacts shows the indicator.
- Pilot test: a node with only internal artifacts, or none, shows no indicator.
- Follow-up regression (executed once WI-039 lands in Milestone 3, not part of this item's own build -
  corrected during this plan's own Pass 7 adversarial review, which found this originally phrased as if
  executable at this item's own Milestone 2 build time): for any node showing the indicator, opening its
  Artifacts tab shows at least one artifact - guards AC-3 as a real invariant, not just an assertion.

### Open Questions

- `[builder]` Indicator glyph and its position within the row - not specified by any wireframe state in
  this design (the cited `#hierarchy` state shows identical icons regardless of content).

### Deliverable

Hierarchy rows show a content indicator exactly when their node has a real, non-internal artifact to
view.
